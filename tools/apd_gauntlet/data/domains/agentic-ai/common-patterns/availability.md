# Agentic AI common patterns — Availability

These are illustrative templates, not all-inclusive. Use them to calibrate analytical style, severity assignment per the agentic-AI rubric, and NIST/ATT&CK mapping habits. The specialist agent's checklist still drives the actual analysis — this file only calibrates how an Availability finding or capability should look once written.

## Common finding patterns

**Pattern: An autonomous task loop or self-improvement loop has no hard ceiling on iterations, tokens, tool calls, wall-clock, or spend that fails closed.**

- Severity: high (high autonomy + unbounded blast-radius: a single run, or one adversarial task, can exhaust a provider quota, a wallet, or a compute budget and convert normal operation into an availability-and-cost denial of service)
- NIST: SC-5, SC-6, SI-13, CP-2(3), RA-3
- Related concerns: resilient (the kill-switch / backpressure behavior once the ceiling is hit); ephemeral (loop turn-budget as a session-lifetime control); integrity (this is the availability face of LLM06 excessive agency — name the blast-radius=Resilient facet where the agency to consume is the root)
- Detail: This is OWASP LLM10 Unbounded Consumption crossed with LLM06 Excessive Agency, instantiating ATLAS LLM Denial of Service (cost/resource exhaustion) and the Cost Harvesting technique against the model endpoint. MAESTRO L1 Foundation Models (token/inference cost), L3 Agent Frameworks (loop control), and L4 Deployment & Infrastructure (compute/quota) all carry the ceiling. In hexo-ai/sia the Feedback Agent rewrites target_agent.py across N generations bounded only by `--max_gen`; if `--max_gen` is unset, mis-set high, or the per-generation token/wall-clock cost is not separately capped, a run can burn the whole budget across multiple provider keys before the benchmark loop terminates — and each generation re-runs the arbitrary-Python Target Agent, multiplying per-generation cost. The pattern requires a hard `--max_gen` ceiling that fails closed PLUS an orthogonal aggregate token/spend/wall-clock budget enforced across generations and across all provider keys, not an iteration count alone.

**Pattern: The agent's critical path depends synchronously on external model-provider (and tool/RAG/vector-store) APIs with no documented SLA, rate-limit headroom, or degraded-mode plan.**

- Severity: high (timeliness is silently inherited from the least-available dependency; a provider 429/5xx, regional outage, or latency spike stalls or fails autonomous task completion with no documented floor)
- NIST: CP-2(8), SC-5, SI-13, SR-3, RA-3
- Related concerns: resilient (provider failover, checkpoint/resume, and fail-the-run-cleanly logic once throttled); distributed (the multi-provider / multi-region topology that supplies the headroom); ephemeral (the provider key as a lifecycle artifact, owned there, not here)
- Detail: OWASP LLM10 Unbounded Consumption crossed with LLM03 Supply Chain, mapping to ATLAS LLM Denial of Service and the availability dimension of ML Supply Chain Compromise. MAESTRO L1 Foundation Models, L4 Deployment & Infrastructure, and L7 Agent Ecosystem (external-service dependency) own this. hexo-ai/sia calls multiple model-provider APIs through the Claude Agent SDK plus OpenHands for the Meta-Agent, Target Agent, and Feedback Agent; a 429 or outage mid-run stalls the generation loop and can corrupt the `runs/run_id/gen_n/` artifact sequence. The pattern requires a documented per-provider availability target, a latency budget (p50/p95/p99), and a rate-limit ceiling; a headroom ratio of provisioned RPM/TPM versus per-generation demand; and a degraded-mode plan that fails cleanly rather than stalling indefinitely.

**Pattern: No declared SLO or error budget for autonomous task completion — no success-ratio target, completion-latency SLI, or decision-timeliness window.**

- Severity: medium (without an SLO you cannot verify the agent meets implicit availability/timeliness commitments, cannot detect silent degradation from a model or prompt change, and cannot prioritize reliability work; escalates when a task's value expires if not completed within a window)
- NIST: CP-2, CP-2(3), SI-13, AU-6, RA-3
- Related concerns: resilient (the degraded-success fallback behavior); integrity (acting past a timeliness boundary is the LLM06 excessive-agency facet — name blast-radius=Resilient)
- Detail: OWASP LLM09 Misinformation (degraded success masquerading as completion) crossed with LLM06 Excessive Agency (acting past a timeliness boundary); ATLAS ML Model Performance Degradation / drift on its observability dimension. MAESTRO L5 Evaluation & Observability, L3 Agent Frameworks, and L6 Security & Compliance carry it. hexo-ai/sia optimizes a scalar metric against a benchmark but declares no SLO for the optimization run itself: no target run success ratio, no per-generation completion-latency SLI, and no error budget that distinguishes a clean failed generation from a stalled or hung one. The pattern requires an SLO for run completion (e.g. the fraction of generations that emit a valid `agent_execution.json` within a wall-clock budget), a per-generation time-to-completion SLI, and burn-rate alerting so a stall or silent degradation is caught rather than discovered at budget exhaustion.

**Pattern: Multi-agent and parallel autonomous runs spawn agents, sub-agents, and execution sandboxes with no provisioned-capacity ceiling or headroom posture.**

- Severity: high (multi-agent fan-out, or an agent that spawns sub-agents, contends for shared TPM/RPM quota, sandbox compute, the orchestrator/event-bus, and shared state stores, so legitimate-shape agent traffic saturates the substrate for all tenants)
- NIST: SC-5, SC-6, CP-2(2), SI-13
- Related concerns: resilient (graceful shed-load / backpressure when concurrency maxes out); distributed (load-distribution topology across endpoints and worker pools that the cap relies on); integrity (the agency to spawn without a ceiling is the LLM06 facet — name blast-radius=Resilient)
- Detail: OWASP LLM10 Unbounded Consumption crossed with LLM06 Excessive Agency; the agentic analogue of application-exhaustion DoS, mapping to ATLAS LLM Denial of Service (resource exhaustion) and Cost Harvesting. MAESTRO L4 Deployment & Infrastructure, L3 Agent Frameworks (orchestration/fan-out), and L7 Agent Ecosystem (multi-agent contention) own the contention surface. hexo-ai/sia writes artifacts under `runs/run_id/gen_n/` and executes the generated `target_agent.py` once per generation; running multiple concurrent runs, or a target that itself fans out work, contends for the same provider quota and the same host compute/disk with no declared concurrent-run ceiling. The pattern requires a hard cap on concurrent agents/runs/sandboxes, a headroom ratio of provisioned capacity (compute, TPM/RPM, run-artifact disk) to observed peak fan-out, and a load-test artifact showing graceful shed-load rather than substrate exhaustion at max concurrency.

**Pattern: No failure-domain or blast-radius analysis for the shared agent substrate — orchestrator, state/memory store, provider key/account, and held-out ground-truth store are unmapped single points of fate.**

- Severity: high (agentic systems concentrate fate-sharing in a few single points; an outage of one shared component silently fails the entire fleet, and with no stated DR RTO/RPO per data class a loss is unrecoverable to a known bound)
- NIST: CP-2, CP-2(8), CP-9, CP-10, SC-36, RA-9
- Related concerns: distributed (the replication/topology change that removes the single point of fate); integrity (poisoning of the ground truth as a correctness attack is routed there — Availability owns only its loss-of-availability SPOF); confidentiality (read-scope of the held-out store is the Confidentiality facet of LLM06)
- Detail: OWASP LLM10 Unbounded Consumption crossed with LLM03 Supply Chain; ATLAS ML Model Performance Degradation on its loss-of-evaluation-availability dimension. MAESTRO L4 Deployment & Infrastructure, L2 Data Operations (ground-truth/artifact stores), and L7 Agent Ecosystem (shared-fate across agents) carry it. In hexo-ai/sia the held-out private ground truth (`data/private/`, `evaluate.py`) is the single component whose loss or corruption invalidates every generation's score and halts the optimization loop — the fitness function's availability single point of failure — while the `runs/run_id/gen_n/` artifacts and the orchestrating loop are unreplicated by default. The pattern requires a failure-domain diagram naming what shares fate (orchestrator, provider key/account, the `data/private/` store, the `agent_execution.json` artifact path), a blast-radius statement per shared component, and DR RTO/RPO per data class — held-out ground truth and prior-generation artifacts in particular — with a tested restore.

**Pattern: Agent health is monitored only as a process-up / port-open / HTTP-200 liveness check, with no progress detection for a hung or non-advancing loop.**

- Severity: medium (a shallow check cannot tell a healthy agent from one hung mid-tool-call, stuck in a non-progressing reasoning loop, retrying a throttled provider, or emitting degraded output; the orchestrator keeps routing tasks to, or keeps budget-burning on, an alive-but-stuck agent until a deadline or budget is blown)
- NIST: SI-4, SI-13, CP-10, AU-6
- Related concerns: resilient (the abort/fail-closed action the watchdog triggers once a stall is detected); integrity (silent quality degradation as the LLM09 misinformation face, named not designed here)
- Detail: OWASP LLM10 Unbounded Consumption crossed with LLM09 Misinformation (silent quality degradation); ATLAS ML Model Performance Degradation. MAESTRO L5 Evaluation & Observability, L3 Agent Frameworks, and L6 Security & Compliance carry the liveness signal. hexo-ai/sia has no deep liveness/progress signal between generations: a Target Agent that hangs on an external call or loops without advancing the scalar metric is indistinguishable, to a shallow check, from one making progress — it simply consumes the per-generation budget. The pattern requires a progress/liveness SLI (a per-generation watchdog timeout, metric-improvement-or-abort, or `agent_execution.json` freshness check) that detects a non-progressing generation and fails it closed rather than letting it run to budget exhaustion.

**Pattern: Tech plan asserts "budgets" or "rate limits" generically without specifying the ceiling value, the dimension (per-run, per-generation, per-provider-key, aggregate), or the fail-closed behavior on breach.**

- Disposition: blocked or uncertainty
- prerequisite_evidence: "Consumption-budget specification — the hard iteration/generation ceiling, the orthogonal aggregate token/wall-clock/spend cap, the dimension each is enforced on (per-run vs per-key vs fleet-aggregate), whether enforcement fails closed, and the provider rate-limit headroom ratio versus per-generation demand"

## Common capability patterns

**Pattern: A hard iteration/generation ceiling that fails closed, paired with an orthogonal aggregate token/wall-clock/spend budget enforced across all generations and all provider keys.** Maturity is nascent when only an iteration count exists; developing once an aggregate spend/token cap is declared; robust when enforcement is shown to fail closed and is enforced across every provider key, not per-key.

**Pattern: Documented per-provider availability target, latency budget (p50/p95/p99), and rate-limit headroom ratio, with a fail-cleanly degraded-mode plan.** `designed` from a dependency-SLA table in the tech plan; `implemented` requires the headroom ratio (provisioned RPM/TPM vs per-generation demand) to be measured; `operationalized` requires evidence the degraded-mode path (failover, checkpoint/resume, clean run-fail) has actually fired.

**Pattern: An SLO/SLI framework for autonomous task completion — run success-ratio SLO, per-generation completion-latency SLI, error budget, and burn-rate alerting.** Higher maturity when burn-rate alerting is wired to detection of a stalled or silently-degraded loop, not merely to budget exhaustion after the fact.

**Pattern: A documented failure-domain map of the shared substrate with per-component blast-radius and per-data-class DR RTO/RPO, backed by a tested restore.** Nascent when the fate-sharing single points (orchestrator, provider key/account, held-out ground-truth store, artifact path) are merely named; robust when each critical data class carries an RTO/RPO and the restore has been exercised.
