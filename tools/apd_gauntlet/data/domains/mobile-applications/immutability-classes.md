# Mobile application required-immutable data classes

For a mobile application and the backend it fronts, the following data classes must not change once written. Immutability findings test storage substrate, retention enforcement, and deletion controls against this list.

**The authoritative immutable copy is server-side.** On-device storage is not a tamper-evident substrate: a rooted device, a Frida-instrumented process, or a restored backup can rewrite anything the app can write. Where a record below has any on-device representation, the immutable record of obligation must live server-side (WORM / object-lock / append-only with hash-chaining), and the device copy is treated as mutable and untrusted. Reuse the multi-regulator retention-pinning pattern (pin to the longest applicable floor and enumerate every floor) where a class is governed by more than one obligation.

- **Consent and tracking-permission records** — the PRIVACY-3 proof-of-consent: scope, timestamp, app version, and the SDK set active at the time of consent, plus the withdrawal record. GDPR Article 6(1)(a) / Article 7 lawful-basis evidence. Withdrawal must be recorded as a new event, never as overwriting the prior grant; the proof-of-prior-consent obligation outlives the consent itself. Retention pinned to the longest of the applicable GDPR documentation duration and any app-store policy floor.
- **Data-subject-rights request and response records (PRIVACY-4)** — DSAR access, erasure, and export requests: receipt, action taken, and the records affected. GDPR Article 12 demonstrability; the request and its disposition are immutable even after the underlying account data is erased (pseudonymized record-of-deletion).
- **Attestation-verification records** — which device and app version presented which attestation verdict (Play Integrity / App Attest) at time T, and the backend's accept/reject decision. The tamper-evidence basis is the server-anchored audit chain; retention pinned to the incident-reconstruction window so a forged-client investigation can be reconstructed after the fact.
- **Authentication and step-up event log** — credential-compromise reconstruction depends on a tamper-evident, server-side authn/step-up record. Retention must match or exceed the longest plausible breach-detection window plus the longest token lifetime issued.
- **Signed-build and app-signing provenance records** — the build digest, signing identity, SBOM, and release version linking source to the binary in the store. Required for repackaging attribution ("is this the build we shipped?") and for the forced-update / kill-switch decision; the link between a version and its provenance must be immutable.
- **Token issuance and revocation records** — proof that a token was issued at time T and revoked at time T′. The stolen-device response (server-side revocation) is unprovable without an immutable revocation record.
- **Security-incident and tamper-signal records** — root/jailbreak/repackaging/attestation-failure events as the breach-detection fact base; alteration erases the evidence that the client was compromised.
- **SDK-collection and data-flow records** — which SDK version collected which fields and shipped them where, retained for privacy-manifest / Data-Safety attestation defensibility (the app store and a regulator can both demand proof the declaration matched reality).

- **App-vetting decision and report records (NIST SP 800-163r1)** — the app-approval/rejection decision, the static/dynamic/human analysis reports it was based on, the organization-defined security-requirements baseline applied, and the reputation signal, all bound to the exact build/version vetted. Required so an organization can prove which version it approved against which requirements at time T and reconstruct or defend a deployment decision; a new build's re-vetting is a new immutable decision, never an overwrite of the prior one. Retention pinned to the longest of the organization's audit-retention policy and the deployment lifetime of any version that decision authorized. Applies only where an organization vets/approves apps before deployment (managed/enterprise distribution); not applicable to pure public-App-Store distribution.

Specialists raise Immutability findings against any class on this list that has mutable storage, an on-device-only record where a server-side immutable copy is required, absent retention controls, deletion-by-single-credential, or unspecified retention. The synthesizer cross-references Non-Repudiation findings on the same data class so the merged record carries both the completeness and the alteration concern; an audit-tampering gap plus an audit-completeness gap on the same consent or attestation class merges into a critical finding under the GDPR accountability and app-store attestation anchors.
