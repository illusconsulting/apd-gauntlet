# Mobile application common patterns — Distributed

These are illustrative templates, not all-inclusive. Use them to calibrate analytical style, severity assignment per the mobile application security rubric, and NIST/ATT&CK mapping habits. The specialist agent's analytical checklist still drives the actual analysis — this file calibrates how findings and capabilities should look once written. This is the smallest, least mobile-native goal: it owns only the topology concerns that touch the fleet — where on-device-synced data and SDK egress land geographically, and which single backend, push, or attestation dependency the whole install base hangs on. Generic backend HA, region failover design, and replica/quorum topology route to api-security; this lens owns the mobile-fleet-specific edge of distribution.

## Common finding patterns

**Pattern: On-device data or third-party SDK egress crosses a data-residency boundary with no lawful-transfer basis.**

- Severity: high (reversibility/data-sensitivity: `cached_pii_phi_on_device` and `health_fitness_data` synced or shipped extra-EEA is an irreversible disclosure to a third jurisdiction; scale-vector: the egress runs in every install, so one undisclosed destination region is a fleet-wide transfer; client-side-only enforcement: a region preference set in app config is not a residency control)
- NIST: SC-7, AC-4, SA-9, PL-9
- Related concerns: confidentiality (the on-device protection of the synced PII/PHI); non_repudiation (the consent/transfer record, PRIVACY-3); the lawful-basis determination and any backend-side residency routing route to api-security, and any token/identity data in the egress routes to identity-security
- Detail: This is MASVS-PRIVACY-1 (minimization and disclosure of what leaves the device) intersecting MASVS-NETWORK egress, in the MASWE privacy/data-collection area. MASTG privacy testing — static and dynamic analysis of network destinations plus review of the iOS privacy manifest and Google Play Data Safety declaration — names where the synced PII/PHI and the SDK's `sdk_collected_field` actually land, which the ATT&CK Mobile data-exfiltration-over-network technique describes as the transfer. CWE-359 (exposure of private personal information). The structural control is server-side: a per-data-class region binding with a documented lawful-transfer basis (adequacy decision or SCCs) for any extra-EEA flow, enforced at the sync/ingest tier, not a client-set region flag. The finding of record is the missing residency invariant on the backend the synced data crosses into and the SDK's undisclosed transfer; the device choosing a region is defense-in-depth at most.

**Pattern: The mobile fleet depends on a single backend endpoint or region with no client-side failover.**

- Severity: medium to high (blast-radius: every install routes to one host/region, so a zonal or regional incident is a total outage for the fleet at once; scale-vector: a single hardcoded base URL or single-region API gateway is the chokepoint for the whole install base, and a deployed binary cannot be re-pointed without an app-store update cycle)
- NIST: SC-7, CP-7, CP-10
- Related concerns: resilient (how the client degrades — offline-first cache, retry/backoff — when the single endpoint is unreachable); availability (the backend SLO target itself); the backend's multi-region/active-active topology routes to api-security, which owns server-side HA design
- Detail: The mobile-specific edge is that the endpoint topology is baked into a binary in the attacker's and the user's hands: a single base URL pinned in the Network Security Config / App Transport Security exception set, or a single region with no DNS/edge-based failover, leaves the fleet unable to fail over without a release. This is the MASWE availability/network-dependency area rather than a specific weakness ID; MASTG network testing inspects the configured endpoints and pinning set to confirm whether more than one reachable path exists. The structural control is a documented backend region topology fronted by an endpoint the client reaches indirectly (DNS or edge routing the operator controls) so failover does not require shipping a new binary, plus a client retry/backoff and offline cache so a transient single-endpoint failure degrades rather than hard-fails. Server-side active-active and replica design is api-security's; this lens owns whether the client can reach an alternate path at all.

**Pattern: Push delivery or device attestation depends on a single provider (Play Integrity / App Attest / FCM / APNs) with no fallback path.**

- Severity: medium to high (blast-radius: a single attestation provider outage means the backend either fails every request that requires a verdict or fails open fleet-wide; scale-vector: one provider dependency spans the entire install base; client-side-only enforcement: an attestation verdict the backend cannot obtain is not a substitute for a server-side authorization decision)
- NIST: SC-7, CP-7, CP-10, IA-9
- Related concerns: authenticity (the `attestation_token_jwt` as the verifiable client-identity signal, and what the backend does when it is unavailable); resilient (the documented fail-open vs fail-closed behavior under provider outage, MASVS-RESILIENCE-4 attestation reliance); availability (push/notification delivery SLO); the verdict-verification logic and the fail-open/fail-closed authorization decision route to api-security / identity-security
- Detail: Play Integrity and App Attest each terminate at a single platform authority (Google / Apple), and FCM / APNs are each single push fabrics — none has a like-for-like fallback, so the topology question is what the backend does when the provider is unreachable, not how to multi-home the provider. This is the MASVS-RESILIENCE-4 device-binding/attestation-reliance facet read as a distribution dependency, in the MASWE resilience/attestation area; MASTG resilience testing examines the attestation flow and whether the verdict is treated as advisory or load-bearing. The structural control is a server-side degradation policy declared in advance — fail-closed for consequential actions and fail-open for low-risk reads, with the verdict scored as one input to a server-side decision rather than the decision — so a single-provider outage degrades gracefully instead of taking the fleet down or silently disabling the only genuineness signal. The provider is a SPOF for the signal; the missing invariant is the backend's pre-declared behavior when the signal is absent.

**Pattern: A bundled third-party SDK ships data to an undisclosed or unbounded set of egress endpoints.**

- Severity: high (scale-vector: one in-process SDK in every install with network capability is a fleet-wide egress channel running at the app's full privilege; reversibility/data-sensitivity: `advertising_id`, `device_identifier`, and `cached_pii_phi_on_device` shipped to an unenumerated destination set is an unrecoverable disclosure; client-side-only enforcement: a consent toggle the SDK can ignore in-process is not an egress control)
- NIST: SC-7, AC-4, SA-9, SR-3
- Related concerns: confidentiality (the on-device data the SDK reads in-process); privacy / non_repudiation (the MASVS-PRIVACY-2 device-identifier collection and the consent/`privacy_manifest_declaration` record); the egress-destination allowlist and any server-side proxying of SDK traffic route to api-security
- Detail: This is MASVS-STORAGE-2 (no unintended data leakage to third parties) intersecting MASVS-PRIVACY-2 (identifier collection), in the MASWE privacy/third-party-data-sharing area; an over-broad SDK is the supply-chain-inside-the-app position from the domain model. MASTG testing — dynamic network capture of SDK destinations cross-checked against the declared privacy manifest / Data Safety form, and SDK inventory against an SBOM — establishes the actual egress topology versus the disclosed one, matching the ATT&CK Mobile data-exfiltration-over-network and the over-permissioned-third-party-code patterns. CWE-359 and CWE-200 (exposure of sensitive information). The structural control is a bounded, disclosed egress destination set: an enumerated SDK egress allowlist verified against the privacy manifest, with provenance/SBOM gating on every SDK build (a new SDK version is a new in-process trust and egress decision), enforced at build and network-policy time rather than trusting the SDK's own consent handling. An SDK that can dial an unbounded destination set is an unbounded transfer surface regardless of the consent UI in front of it.

**Pattern: Tech plan asserts multi-region or multi-provider distribution generically without specifying the active fleet topology — which data classes are region-bound, which endpoint/push/attestation provider the client actually reaches, and what the client does on its loss.**

- Disposition: blocked or uncertainty
- prerequisite_evidence: "Mobile-fleet distribution topology — per-on-device-data-class region binding with lawful-transfer basis for any extra-EEA sync or SDK egress; the enumerated SDK egress destination set cross-checked against the privacy manifest / Data Safety declaration; whether the client reaches the backend through operator-controlled DNS/edge routing (re-pointable without a release) or a single hardcoded endpoint; and the backend's declared fail-open vs fail-closed behavior for attestation and push under a single-provider outage"

## Common capability patterns

**Pattern: Documented backend region topology that the mobile client reaches through operator-controlled routing, with client-side failover and offline degradation.** Maturity: designed when the tech plan names the region topology and states the client reaches the backend via DNS/edge routing the operator can re-point without an app-store release (rather than a hardcoded base URL); implemented when the Network Security Config / App Transport Security and client networking layer show the indirected endpoint plus retry/backoff and an offline cache; tested when a forced single-endpoint or single-region failure is exercised and the fleet fails over (or degrades to offline-first) without a binary update; operationalized when failover routing and the fleet's degradation behavior are monitored in production and a real regional incident has been ridden out without a release.

**Pattern: Bounded, disclosed SDK egress destination set verified against the privacy manifest and gated by SBOM provenance.** Maturity: designed when the SDK inventory enumerates each SDK's intended egress destinations and the data classes it carries, matched to the iOS privacy manifest and Google Play Data Safety declaration; implemented when an egress allowlist (network policy or proxying) and SBOM/provenance gating are wired into the build so an undeclared destination or an unvetted SDK version fails the pipeline; tested when dynamic network capture confirms runtime SDK destinations match the disclosed set with no undeclared egress; operationalized when SDK egress is monitored against the allowlist in production and every SDK version bump re-runs the egress and provenance check as a fresh in-process trust decision.

**Pattern: Data-residency enforcement for synced on-device data, with per-data-class region binding and a lawful-transfer basis.** Maturity: designed when each synced on-device data class (`cached_pii_phi_on_device`, `health_fitness_data`, identifiers) has a declared region binding and a lawful-transfer basis for any extra-EEA flow; implemented when residency is enforced at the sync/ingest tier (server-side routing or storage-level region constraints) rather than a client-set region flag, with the transfer disclosed in the privacy manifest / Data Safety form; tested when network and ingest evidence confirms synced data and SDK egress land only in the bound region(s); operationalized when cross-border egress is monitored, the consent/transfer record (PRIVACY-3) is retained per the immutability obligation, and a residency drift triggers an alert rather than a silent extra-EEA flow.
