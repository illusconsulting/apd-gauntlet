# Mobile application common patterns — Resilient

These are illustrative templates, not all-inclusive. Use them to calibrate analytical style, severity assignment per the mobile application security rubric, and NIST/ATT&CK mapping habits. The specialist agent's analytical checklist still drives the actual analysis — this file calibrates how findings and capabilities should look once written. Resilient owns the graceful-degradation and fail-open-versus-fail-closed decision for mobile-specific controls; the eight MASVS categories are cross-cutting, not goals, so name the confidentiality/integrity/authenticity facet a control also touches in Related concerns rather than re-litigating it here. Hold the central doctrine in view: client-side enforcement of a server-side control is not a control — a degradation mode that fails open on the device is bypassable on a rooted/Frida-instrumented client, so the finding of record is the missing server-side invariant that should govern when the client signal is absent.

## Common finding patterns

**Pattern: Certificate / public-key pinning has no graceful path — a pinned-leaf rotation bricks every installed client (pin brittleness), or pin-validation failure silently fails open and the connection proceeds unpinned.**

- Severity: high (the brittleness face is a self-inflicted fleet-wide availability outage on certificate rotation with no client-side remediation short of an app-store update; the fail-open face drops to defense-in-depth on stock devices but the client-side-only-enforcement and blast-radius modifiers load because a fleet-wide silent unpin re-exposes a credential/PII channel to a user-installed MitM CA at scale)
- NIST: SC-8, SC-13, SC-23, SI-13, CM-3, IA-5
- Related concerns: availability (the rotation-outage face is an Availability event the merged record carries); confidentiality (the channel the unpin re-exposes); routes to api-security for the server-side TLS termination and certificate-lifecycle decision, and to identity-security for any token presented on the channel
- Detail: MASVS-NETWORK-2 (pinning) with the MASWE insufficient-transport-protection / pinning-bypass area, tested by the MASTG techniques for bypassing certificate pinning (static patching of the pin set and dynamic Frida hooks on the `TrustManager` / `URLSession` delegate path), CWE-295 (improper certificate validation). The ATT&CK Mobile technique is adversary-in-the-middle on network traffic. Pinning to a single leaf certificate's SPKI with no backup pin is the brittleness root cause — when the operator rotates the leaf, every client whose pin set predates the rotation cannot connect and only an app-store update recovers them; pinning the intermediate or carrying a backup pin set is the structural control. The fail-open root cause is a pin-mismatch handler that logs and proceeds rather than aborting the connection; the structural control is a fail-closed pin check whose `pinning_public_key_set` is rotatable out-of-band (remote-config-delivered, signed, with overlap) so rotation never requires a binary push and a mismatch is treated as a security event shipped to the server, not a client-only block.

**Pattern: Attestation / device-integrity verdict fails OPEN — when Play Integrity / App Attest is unavailable, times out, rate-limits, or returns an error, the app keeps acting and the backend accepts the request as if a genuine verdict had been presented.**

- Severity: critical to high (critical when the backend consumes a client-asserted "attestation passed" flag and the unavailable-verdict path lets a patched client transact as genuine at fleet scale — the client-side-only-enforcement modifier converts a device-local bypass into a backend write; high when the verdict is advisory and only a degraded signal is lost, with no server-trusted decision behind it)
- NIST: SI-4, SI-7, IA-9, RA-3, CP-12, AU-2
- Related concerns: authenticity (the attestation verdict is the *verifiable* client identity — its forgery/replay/staleness face is Authenticity's); integrity (the tamper signal); routes to api-security for the server-side verdict-verification endpoint and to identity-security for any attestation-bound token issuance
- Detail: MASVS-RESILIENCE-1 (platform/integrity detection) and MASVS-RESILIENCE-4 (the device-binding/attestation face), with the MASWE area for missing or improperly-validated attestation and for treating an absent integrity signal as a pass; MASTG knowledge and tests for attestation verification and for verdict-replay/staleness, CWE-636 (not failing securely / fail-open) and CWE-345 (insufficient verification of data authenticity). The ATT&CK Mobile angle is the compromised/rooted device evading detection. The doctrine governs: `attestation_token_jwt` is freshness-sensitive and the backend's verification outcome — pass, fail, or verdict-unavailable — is the audit anchor, never a client `RESILIENCE` block. The structural control is an explicit fail-safe server-side default: a missing, errored, stale, or rate-limited verdict denies or steps the request down to a low-trust path on the backend, never grants; the missing server-side invariant is "no genuine, fresh verdict, no high-trust action," enforced where the verdict is verified, not on the device that produced it.

**Pattern: App degrades unsafely on an outdated / EOL platform — when the device OS no longer provides a security primitive (hardware-backed Keystore/StrongBox, Secure Enclave, BiometricPrompt class-3, modern TLS), the app silently falls back to a weaker mode instead of refusing the sensitive operation.**

- Severity: high to medium (high when the silent fallback drops a `keystore_keychain_key` to software-only storage or downgrades transport such that secrets/tokens become client-extractable or interceptable on the install base's long tail of old devices; medium when a compensating control is present and only a defense-in-depth rung is lost)
- NIST: CM-2, SC-13, SC-28, SI-7, RA-3
- Related concerns: confidentiality (the key/secret the weak fallback exposes); integrity (the platform integrity floor); routes to api-security for the server-side minimum-platform-policy enforcement that the client floor must mirror
- Detail: MASVS-CODE-1 (platform/SDK currency and the minimum-OS floor) with the MASWE area for outdated platform usage and insecure cryptographic fallback, tested via the MASTG techniques for checking the target/minimum SDK floor and key-storage backing, CWE-757 (algorithm/security-level downgrade) and CWE-311 (missing encryption on the fallback path). The structural control is a fail-closed capability gate: the app must detect that the hardware key store, Secure Enclave, or required TLS profile is unavailable and refuse to provision or release the secret rather than transparently falling back to `exportable` software keys or a downgraded cipher — and because that gate runs on an adversary-controlled client, the missing server-side invariant is a minimum-attested-platform policy the backend enforces, so an EOL device that lost the security feature is steered to a degraded, non-secret-bearing mode by the server, not trusted on the strength of a client claim.

**Pattern: No backoff / jitter on retries against the backend — a backend blip, a forced token refresh, or a push-triggered sync makes the whole installed fleet retry in lockstep, a synchronized mobile-fleet retry storm (thundering herd) that turns a brief outage into a self-sustained one on recovery.**

- Severity: high (the scale-vector modifier dominates: millions of clients re-attempting on a fixed interval, or all waking on the same push/cron, synchronize into a self-DDoS that prevents recovery; a retried non-idempotent transaction additionally produces duplicate backend side-effects — double funds movement, double mutation)
- NIST: SI-13, SC-5, CP-10
- Related concerns: availability (the backend-saturation ceiling the storm hits); integrity (idempotency of the retried `consequential backend transaction` — retry without an idempotency key is duplicate-mutation risk); distributed (load spread across backend failure domains); routes to api-security for the server-side admission control / load-shed that must survive the herd
- Detail: MASVS-CODE-3 (sound implementation practices on the network client) with the MASWE area for improper retry/error handling, tested by the MASTG techniques for observing client retry behavior under induced backend failure, CWE-770 (allocation/requests without limiting) on the fleet aggregate. The ATT&CK Mobile relevance is endpoint denial-of-service driven from the client population. The structural control is exponential backoff with full jitter and a per-dependency retry budget on every backend call, plus de-synchronized scheduling so push-/cron-woken syncs spread over a window rather than firing at one instant; retried side-effecting calls must carry an idempotency key. Because client-side backoff alone is bypassable on a patched client and absent on old versions, the missing server-side invariant is backend-side admission control, rate limiting, and load-shed (Retry-After honored, but not relied upon) so the backend survives a fleet that misbehaves.

**Pattern: Blast radius of a single malicious or vulnerable in-process third-party SDK is unbounded — analytics/ads/crash SDKs run with the app's full privilege and there is no capability isolation, so one bad SDK reaches all on-device storage, tokens, keys, and network.**

- Severity: critical to high (the backdoored-SDK scale-vector reaches every user's `stored_session_and_refresh_tokens`, `cached_pii_phi_on_device`, and `keystore_keychain_key` across the install base in one shipped build — critical when the SDK has network plus storage plus reflection capability; high when capability is narrower or the data reached is lower-sensitivity)
- NIST: SA-9, SA-12, CM-7, AC-6, SC-7, SI-7
- Related concerns: confidentiality (the in-process data the SDK can read); ephemeral (a kill/disable path to expire a compromised SDK's reach without a binary push); non-repudiation (the SDK-egress record the consequential-action surface requires); routes to api-security for any server-side scoping of what the SDK's calls may do
- Detail: MASVS-CODE-2 (software composition and third-party-component risk) with the MASWE area for vulnerable/over-permissioned dependencies, informed by NIST SP 800-163 app-vetting and SBOM/provenance practice, CWE-829 (inclusion of functionality from an untrusted control sphere) and CWE-1357 (reliance on insufficiently trustworthy component). The ATT&CK Mobile angle is the supply-chain compromise of a bundled library exfiltrating data in-process. The structural control bounds the fault domain: pin and verify SDK provenance (SBOM, signature, version pinning), minimize each SDK's granted capability and the data it can reach, prefer out-of-process or sandboxed delivery (WebView-isolated or separate-process where the platform allows) over an in-process bridge, and carry a remote disable so a compromised SDK can be cut off fleet-wide without an app-store round-trip. Because no in-process boundary fully contains a same-process library on a rooted device, the missing server-side invariant is that the backend never trusts an SDK-originated signal as authorization and records SDK network egress as a server-side fact.

**Pattern: Forced-update / minimum-version gate failure mode is undefined — when the version check is unreachable, disabled, or the client simply ignores it, known-vulnerable client builds keep transacting against the backend (the resilience face of the kill-switch).**

- Severity: high to medium (high when a known client CVE is live and the undefined failure mode lets the vulnerable fleet keep reaching consequential backend transactions — the scale-vector and blast-radius modifiers load because one bypassed gate keeps the entire vulnerable population alive; medium as a latent hygiene gap with no current known-vulnerable build)
- NIST: SI-2, CM-3, CM-7, RA-5, CP-12
- Related concerns: integrity (the signed-build/version provenance the gate decision rests on); availability (the gate must not itself brick good clients when its config service is down); routes to api-security for the server-side version-policy enforcement and to identity-security for refusing token issuance to a sunset client
- Detail: MASVS-CODE-4 (the forced-update / minimum-version kill-switch) with the MASWE area for a missing or bypassable update-enforcement mechanism, tested by the MASTG techniques for observing version-gate behavior and patching the client-side check, CWE-1188 / improper enforcement of a security-relevant version policy and CWE-636 on the unreachable-gate fail-open. The doctrine is decisive: a version gate evaluated only on the device is bypassable by a patched client, so the structural control places the decision server-side — the backend refuses or degrades service (and identity-security refuses token issuance) to a client whose version is below the floor, with the on-device prompt as UX only. The failure mode must be defined and fail-closed for the sunset cohort: a client that cannot reach the version-policy service is denied the high-trust path, not waved through, while a good current client is never bricked by a config-service outage (the floor is cached and the deny applies only to a positively-identified stale version).

**Pattern: Tech plan describes "retries," "pinning," "attestation," or a "min-version check" generically without specifying the backoff/jitter curve and per-dependency budget, the backup-pin and rotation path, the verdict-unavailable behavior, or the fail-safe-versus-fail-open degradation mode of each control.**

- Disposition: blocked or uncertainty
- prerequisite_evidence: "Resilience-and-degradation specification — for pinning: backup-pin set, out-of-band rotation/overlap path, and pin-mismatch handler behavior (abort vs. proceed); for attestation/integrity: the server-side default on verdict-unavailable/errored/stale/rate-limited (deny/step-down vs. accept); for backend calls: backoff curve, jitter strategy, per-dependency retry budget, push/cron de-synchronization, and retried-call idempotency-key contract; for EOL-platform fallback: which security primitive may degrade and whether the app refuses vs. silently falls back; for SDKs: per-SDK capability scope and the remote-disable path; and for the version gate: where the decision is enforced and the documented failure mode when the policy service is unreachable"

## Common capability patterns

**Pattern: Pin rotation with a backup-pin set and a soft-fail-to-report path that does not brick clients.** Maturity: designed when the architecture names a backup pin (intermediate or a second SPKI) and an out-of-band, signed pin-delivery channel rather than a hardcoded single leaf; implemented once the Network Security Config / App Transport Security pin set carries overlapping pins and the pin-mismatch handler aborts the connection and emits a security event to the server (fail-closed, not silent-proceed); tested when a pinning-bypass attempt (static patch and Frida hook on the trust evaluation) is shown to be caught and reported and a staged certificate rotation is exercised end-to-end without an app-store push; operationalized when the rotation runbook, overlap window, and pin-mismatch alerting are live and a rotation has been performed in production with zero client lockout.

**Pattern: Fail-safe (not fail-open) on attestation / integrity-check failure.** Maturity: designed when the policy explicitly states that a missing, errored, stale, or rate-limited Play Integrity / App Attest verdict denies or steps the request down rather than granting; implemented once the backend verdict-verification endpoint enforces that default and treats freshness as mandatory, with the client carrying no authorization weight; tested when verdict-unavailable, replayed-verdict, and stale-verdict cases are exercised against the backend and shown to deny/step-down, and a rooted/Frida client cannot transact on the high-trust path; operationalized when the verification outcomes (pass/fail/unavailable) are recorded server-side as the audit anchor and alerting fires on a fail-open regression or a spike in unavailable verdicts.

**Pattern: Retry-with-jitter plus a per-dependency retry budget on backend calls, with fleet de-synchronization and idempotent side-effects.** Maturity: designed from a tech-plan statement of the backoff curve, full-jitter strategy, and per-dependency budget; implemented once the network client is configured with exponential backoff and jitter, push/cron-woken syncs are spread over a window rather than firing at an instant, and side-effecting calls carry idempotency keys; tested with a game-day or chaos exercise that induces a backend blip and shows the client population does not synchronize into a recovery-blocking storm and that a retried transaction does not double-apply; operationalized when fleet-aggregate retry behavior is observable, Retry-After is honored client-side while backend admission control / load-shed is the relied-upon control, and the herd has been survived in production.

**Pattern: Bounded blast radius around third-party SDKs.** Maturity: designed when each SDK's capability and data reach are scoped in the architecture, provenance (SBOM, signature, pinned version) is required, and a remote-disable path exists; implemented once SDKs are version-pinned and provenance-verified at build, capability is minimized (out-of-process or WebView-isolated delivery preferred over an in-process bridge where the platform allows), and the kill/disable switch is wired; tested when an SDK is shown unable to reach `keystore_keychain_key`, tokens, or PII outside its scoped surface and the remote-disable cuts it off without an app-store round-trip; operationalized when SDK initialization, granted capability, version changes, and network egress are recorded server-side per the consequential-action surface, and the backend trusts no SDK-originated signal as authorization.
