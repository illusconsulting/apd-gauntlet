# Mobile application common patterns — Availability

These are illustrative templates, not all-inclusive. Use them to calibrate analytical style, severity assignment per the mobile application security rubric, and NIST/ATT&CK mapping habits. The specialist agent's analytical checklist still drives the actual analysis — this file calibrates how findings and capabilities should look once written. This lens owns the mobile app's own reachability and responsiveness and its dependence on the backend — whether the client survives a slow, hostile, or absent backend and whether attacker-controlled inbound input can take the app down. The backend's uptime target and server-side capacity belong to api-security; this lens owns the client-side failure behavior and the inbound-input crash surface. Graceful-degradation mechanics (retry/backoff, fail-open vs fail-closed, pin-rotation brittleness) are Resilient's; route to it via related_concerns.

## Common finding patterns

**Pattern: Network calls have no timeout or cancellation, so the UI or main thread hangs on a slow or hostile backend.**

- Severity: medium to high (device-trust assumption: no special device needed — a slow network or a `network_mitm` holding the connection open hits stock devices; blast-radius: a blocked main thread is a per-device hang, but a synchronous call on a hot path can ANR/freeze the app for every user behind a degraded backend; client-side-only enforcement: there is no server-side fix for a client that waits forever)
- NIST: SC-5, SC-5(1), SI-13
- Related concerns: resilient (the retry/backoff and per-dependency budget that bound repeated failures, and circuit-breaking); the backend SLO and server-side capacity route to api-security
- Detail: This is the MASWE availability / improper-resource-handling area read at design altitude (MASVS-CODE addresses robust client behavior). A networking call with no read/connect timeout and no cancellation on view dismissal means a slow backend, a captive portal, or an adversary on the path (the ATT&CK Mobile network-effects pattern of holding or degrading a connection) freezes the UI thread and triggers an Android ANR or an iOS watchdog kill. CWE-400 (uncontrolled resource consumption). The structural control is a timeout and cancellation discipline on every I/O — bounded connect/read timeouts, cancellation tied to the screen lifecycle, and work moved off the main thread — so a degraded dependency degrades the screen, not the process. The backend's responsiveness is api-security's; this lens owns whether the client tolerates the backend being slow.

**Pattern: A malformed deep link, intent, push payload, or server response crashes the app (denial of service via inbound input).**

- Severity: medium to high (device-trust assumption: a `phishing_deep_link_or_ipc_caller` or a `compromised_backend_or_response` reaches a stock device with a crafted payload, no root required; blast-radius: a crash-on-launch deep link a co-resident app or a link can fire is a remotely-triggerable per-device DoS, and a poisoned server response crashes every client that fetches it; reversibility: a crash loop on a persisted bad payload can brick the app until reinstall)
- NIST: SI-10, SC-5, SI-11
- Related concerns: integrity (the same inbound-untrusted-input boundary — the validation gap that lets the malformed input through is Integrity's, MASVS-PLATFORM-1 / CODE-3); resilient (safe-fail and recovery from a poisoned cached payload)
- Detail: This is the availability face of MASVS-PLATFORM-1 (IPC/deep-link handling) and MASVS-CODE-3 (validation of untrusted input the client consumes), in the MASWE platform/input-handling area; the attacker positions are the phishing-deep-link caller and the untrusted-server-response. Unchecked parsing of `deep_link_parameters`, `intent_extras`, `push_payload`, or an `untrusted_server_response` (an unexpected type, a missing field, an oversized array, a malformed JSON/PDF in the WebView viewer) throws an unhandled exception and crashes the process — matching the ATT&CK Mobile input-injection / application-crash patterns. CWE-20 (improper input validation), CWE-248 (uncaught exception). The structural control is defensive parsing at every inbound entry point with a safe-fail UI (reject and surface an error, never crash), and never re-launching into a persisted poisoned payload. The validation boundary itself is Integrity's finding; this lens owns the crash as the user-visible availability impact.

**Pattern: A hard dependency on a single backend with no offline or degraded mode leaves core flows unusable whenever the backend is unreachable.**

- Severity: medium (blast-radius: every install is dead-in-the-water during a backend incident or while the user is offline; reversibility: transient, but a banking/health app that cannot even show a cached balance offline fails its core promise; device-trust assumption: no attacker needed — a network outage suffices, though a `network_mitm` can induce it)
- NIST: CP-2, CP-10, SC-5
- Related concerns: resilient (the retry/backoff, circuit-breaking, and how the client degrades rather than spins); distributed (whether the client can reach an alternate backend endpoint/region at all); the backend's own HA and SLO route to api-security
- Detail: A mobile client is frequently offline or on a degraded network by nature, so a design that treats the backend as always-present is an availability gap rather than only a backend concern. This is the MASWE availability / offline-handling area; MASVS-CODE robust-operation expectations apply. With no offline cache for read flows and no degraded mode, a backend outage or a subway tunnel makes core screens unusable, and a thundering-herd reconnect on recovery (Resilient's concern) compounds it. CWE-400 / CWE-703 (improper check or handling of exceptional conditions). The structural control is an offline-first or degraded-mode design for core read flows (serve last-known cached `cached_pii_phi_on_device` with a clear staleness indicator) and a clear, non-blocking error state for write flows, so the client is useful — or at least honest — when the single backend is unreachable. Server-side HA is api-security's; this lens owns whether the client has any behavior at all when the backend is gone.

**Pattern: A WebView rendering untrusted or remote content is an uncontrolled crash and hang surface.**

- Severity: medium (device-trust assumption: a `compromised_backend_or_response` or a hostile ad/marketing payload reaches a stock device; blast-radius: a WebView crash or memory blow-up takes the host process with it on a per-device basis; reversibility: transient, but a WebView wired to load attacker-influenced URLs can be driven into repeated crashes)
- NIST: SC-5, SI-10, SI-13
- Related concerns: integrity (the WebView as the untrusted-content-to-native boundary, MASVS-PLATFORM-2 — the JS-bridge exposure is Integrity's); confidentiality (data the WebView can exfiltrate outward); resilient (isolating the WebView so its failure does not take the app down)
- Detail: A `WKWebView` / Android `WebView` that loads remote marketing content or renders a server-supplied PDF/HTML is a full rendering engine consuming attacker-influenceable input in-process. This is the availability edge of MASVS-PLATFORM-2 (WebView usage), in the MASWE platform/WebView area; MASTG platform testing examines WebView configuration and the content it loads. A malformed document, an infinite-redirect, or a memory-exhausting page hangs or crashes the host process. CWE-400 / CWE-1188 (insecure default initialization of resource). The structural control is to load only trusted, integrity-checked content, bound WebView resource use, and isolate the WebView (separate process where the platform allows) so its failure degrades a screen rather than the app. The JS-bridge and data-leak facets are Integrity's and Confidentiality's; this lens owns the WebView as a crash surface.

**Pattern: A forced-update or version-gate hard-bricks the app instead of degrading gracefully.**

- Severity: medium (blast-radius: a kill-switch with no graceful path can lock out the entire install base at once — the inverse availability risk of the CODE-4 control existing; reversibility: users are stranded until they can reach the store and update, which is not always immediate; client-side-only enforcement: the gate is correctly server-driven, so the failure mode is a UX/availability choice, not a security bypass)
- NIST: CP-2, CP-10, SI-13
- Related concerns: ephemeral (the forced-version sunset / minimum-supported-version mechanism itself, MASVS-CODE-4, is Ephemeral's); resilient (the graceful-degradation path when an update is required but not yet available); the server-side version-gate decision routes to api-security
- Detail: A minimum-supported-version gate is a necessary control (Ephemeral owns sunsetting vulnerable clients), but its availability failure mode is its own finding: a hard block that shows only "update required" with no read-only or grace-period path strands every below-threshold client at once, and a buggy gate (or one tripped by a store-propagation delay) is a self-inflicted fleet outage. This is the availability reading of MASVS-CODE-4; CWE-703 (improper handling of exceptional conditions). The structural control is a graceful forced-update UX — a grace window, a read-only degraded mode where safe, and a clear path to the store — rather than an immediate hard brick, with the gate threshold and rollout staged so a bad gate cannot lock out the fleet instantly. The sunset policy is Ephemeral's; this lens owns that enforcing it does not itself become the outage.

**Pattern: Tech plan asserts offline support, retries, or resilient networking generically without specifying timeout discipline, the degraded-mode definition, or the behavior on backend or inbound-input failure.**

- Disposition: blocked or uncertainty
- prerequisite_evidence: "Client availability behavior — per-call connect/read timeout and cancellation policy; the defined offline/degraded mode for each core read and write flow (what is cached, staleness indication, write-flow error state); defensive-parsing and safe-fail behavior for each inbound source (deep link, intent, push, server response, WebView content); WebView content trust and isolation posture; and the forced-update UX (grace window vs immediate hard block) so the version gate cannot itself brick the fleet"

## Common capability patterns

**Pattern: Timeout and cancellation discipline on all network and disk I/O, with work off the main thread.** Maturity: designed when the tech plan states per-call connect/read timeouts, cancellation tied to the screen/view lifecycle, and a no-blocking-the-main-thread rule; implemented when the networking layer (URLSession / OkHttp / Retrofit configuration) shows bounded timeouts and cancellation wired to lifecycle, with I/O off the UI thread; tested when a deliberately slow or held-open backend (and a `network_mitm` stalling the connection) is exercised and the UI stays responsive and surfaces a timeout rather than hanging; operationalized when ANR / watchdog-kill and request-latency telemetry are monitored in production and a regression in main-thread stalls raises an alert.

**Pattern: Defensive parsing of every inbound external input with a safe-fail UI and no crash-loop on a poisoned payload.** Maturity: designed when each inbound source (deep link, intent, push payload, server response, imported file, WebView content) has a declared validation-and-reject rule and a safe-fail error state; implemented when the entry points validate types/fields/sizes and catch parse failures, rejecting to an error UI rather than throwing, and a persisted bad payload is not re-launched into; tested when malformed and oversized payloads from a `phishing_deep_link_or_ipc_caller` and a `compromised_backend_or_response` are fuzzed against every entry point with no crash; operationalized when crash-free-session rate and crash clustering by inbound source are monitored and a spike in input-driven crashes triggers investigation. (The validation boundary itself is Integrity's; this is its availability face.)

**Pattern: Offline-first or degraded mode for core read flows, with a clear non-blocking error state for writes.** Maturity: designed when the tech plan names which core flows work offline, what is cached (with staleness indication), and the write-flow behavior when the backend is unreachable; implemented when an offline cache serves core reads and write flows show a clear, non-blocking error and queue-or-reject policy; tested when the backend is taken away (airplane mode / induced outage) and core flows degrade usefully rather than hanging or crashing; operationalized when offline usage and reconnect behavior are monitored and a backend incident is ridden out with the client degrading rather than dying. (Cross-cuts Resilient for the retry/backoff that avoids a reconnect storm.)

**Pattern: Graceful forced-update UX with a grace window and a safe degraded path rather than an instant hard brick.** Maturity: designed when the minimum-supported-version gate (Ephemeral's control) is paired with a documented grace window, a read-only degraded mode where safe, and a clear store path; implemented when the client honors the server-driven gate with a non-blocking grace UI and staged rollout rather than an immediate lockout; tested when a version-gate trip is exercised and below-threshold clients degrade gracefully without a fleet-wide instant lockout; operationalized when the gate rollout is staged and monitored so a misconfigured threshold cannot strand the install base, with the sunset policy itself owned by Ephemeral.
