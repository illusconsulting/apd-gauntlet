# Mobile application common patterns — Confidentiality

These are illustrative templates, not all-inclusive. Use them to calibrate analytical style, severity assignment per the mobile application security rubric, and NIST/ATT&CK mapping habits. The specialist agent's analytical checklist still drives the actual analysis — this file calibrates how findings and capabilities should look once written, not what to look for.

The eight MASVS categories are cross-cutting, not goals. Confidentiality owns at-rest protection of on-device secrets and PII (MASVS-STORAGE-1/2, the data-protection face of MASVS-CRYPTO-1 and the key-protection face of MASVS-CRYPTO-2), in-transit payload confidentiality (MASVS-NETWORK-1), UI and system-surface leakage (MASVS-PLATFORM-3), outbound leakage via WebView bridges, exported components, and in-process SDK egress, and reverse-engineering resistance (MASVS-RESILIENCE-2) as defense-in-depth only — behind "do not trust the client with the secret." Client-side enforcement of a server-side control is not a control: where a confidentiality measure runs only on the adversary-controlled device, it raises attacker cost but is bypassable on a rooted or Frida-instrumented client; score it as defense-in-depth and make the finding of record the missing server-side invariant (server-side token revocation, a secret that never ships to the client at all). This pack is client-focused and composes with the api-security and identity-security packs in a multi-domain run; route server-side authz and business-rule enforcement to api-security and token-issuance / OAuth / OIDC protocol decisions to identity-security via the Related concerns line.

## Common finding patterns

**Pattern: Sensitive data — access/refresh tokens, PII/PHI, keys — persisted in unprotected on-device storage (plist, `SharedPreferences`, unencrypted SQLite, plain files, `NSUserDefaults`) rather than the Keystore/Keychain, readable from a device backup or a stolen device.**

- Severity: high (reversibility/data-sensitivity loads — a long-lived `stored_refresh_token` or `cached_pii_phi_on_device` extracted off a stolen or backed-up device replays for its full lifetime; escalates toward critical when the same store is shared or world-readable so a co-resident app reads it without theft, and when the token has no server-side revocation)
- NIST: SC-28, SC-28(1), IA-5, MP-6, SC-12
- Related concerns: integrity (the same store, if attacker-writable, is an inbound-tamper surface — routed there); ephemeral (token lifetime, rotation, and the server-side revocation that makes an extracted token worthless — couples to identity-security for issuance and api-security for the revocation endpoint); authenticity (device-binding that makes a token non-replayable off-device)
- Detail: MASVS-STORAGE-1 with the MASWE insecure-data-storage area; MASTG exercises this with the data-storage-on-the-filesystem tests and the device-backup inspection technique (Android `adb backup` / auto-backup, iOS encrypted-backup extraction), CWE-312 Cleartext Storage of Sensitive Information and CWE-922 Insecure Storage. The data-at-rest threat model here is the `physical_thief_with_stolen_device` and `co_resident_malicious_app` positions across the `app_sandbox_to_other_apps` boundary, with the ATT&CK Mobile data-from-local-storage technique describing the read. The structural control is hardware-backed storage — secrets in the Android Keystore / iOS Keychain (with an appropriate `kSecAttrAccessible` class and `android:allowBackup="false"` / backup exclusion) and PII in an encrypted store whose DEK is Keystore-wrapped — and the finding of record for any token is the missing server-side invariant: server-side revocability and device-binding, so an extracted token is dead. On-device protection is the at-rest layer, not the control of last resort.
- MAS mapping: MASVS-STORAGE-1; MASWE-0006

**Pattern: An embedded API key, hardcoded secret, or shared signing key is recoverable from the binary by static analysis — fleet-wide, and obfuscation only delays it.**

- Severity: critical (the scale-vector and all-users blast-radius modifiers both load — one `embedded_api_key` / `hardcoded_secret` shipped in every install grants backend or third-party access for the entire fleet, and reversibility is nil once it is extracted and used; the device-trust assumption is minimal because static analysis needs only a copy of the published IPA/APK)
- NIST: IA-5, IA-5(7), SC-12, SC-28, SR-3
- Related concerns: ephemeral (rotation cadence and revocation-after-leak of whatever the key unlocks); authenticity (a shared client signing key undermines provable app/device identity — couples to the Play Integrity / App Attest attestation capability); resilient (obfuscation/anti-decompilation is the cost-raiser layer, owned below as defense-in-depth, never as the control)
- Detail: MASVS-CRYPTO-2 (key-protection) compounded by MASVS-RESILIENCE-2 (anti-static-analysis), with the MASWE hardcoded-cryptographic-key / hardcoded-secret area and CWE-798 Use of Hard-coded Credentials. MASTG covers it with the static-analysis and string/secret-extraction techniques over a decompiled APK (apktool/jadx) or IPA (class-dump / strings over the Mach-O), the `reverse_engineer_with_ipa_apk` position. The ATT&CK Mobile technique is supply-chain / unsecured-credentials harvested from application packages. There is no on-device fix: a secret that ships in the binary is not confidential, so the structural control is architectural — the secret must never reach the client. Replace it with a public OAuth `client_id` plus a backend-mediated exchange (route token issuance to identity-security), an ephemeral per-session credential brokered server-side, or a backend proxy that holds the third-party key and enforces the call. Code obfuscation (below) is defense-in-depth that raises extraction cost; it is not a mitigant for this finding. For hybrid apps the JavaScript/Dart bundle (`js_app_bundle_and_ota_channel`) is the same exposure as the native binary and often worse: a React Native / Capacitor bundle is frequently shipped minified-but-recoverable (or plain), so any key, endpoint, or trusted logic baked into the bundle or its OTA payload is extractable from the package — the no-client-trusted-secret rule applies to the JS bundle exactly as to the compiled binary.
- MAS mapping: MASVS-CRYPTO-2, MASVS-RESILIENCE-2; MASWE-0013

**Pattern: Sensitive data leaks to system surfaces — clipboard, keyboard/predictive-text cache, the task-switcher screenshot / app-backgrounding snapshot, or autofill.**

- Severity: high (data-sensitivity loads when `clipboard_contents`, `keyboard_cache`, `screenshot_snapshot`, or `autofill_data` carries tokens, PII/PHI, or a typed credential; lower toward medium when the leaked surface is non-sensitive, higher when the device-trust assumption is low — the OS-persisted snapshot or co-resident clipboard read needs no rooted device)
- NIST: SC-28, AC-4, SI-12, SC-8
- Related concerns: non_repudiation (where the platform makes a screenshot or clipboard capture of a sensitive surface detectable, it is a consequential-action audit event — routed there); integrity (autofill and clipboard are also inbound paste surfaces); privacy (keyboard learning of a typed secret is a PRIVACY exposure)
- Detail: MASVS-STORAGE-2 (data leaked to system surfaces) with MASVS-PLATFORM-3 (the UI / screenshot face), the MASWE sensitive-data-in-system-surfaces area, and CWE-200 Exposure of Sensitive Information. MASTG tests this with the clipboard, keyboard-cache, and backgrounding-snapshot techniques on both platforms. The `co_resident_malicious_app` position reads a global clipboard or the predictive-text store across the `app_sandbox_to_other_apps` boundary; the OS itself persists the snapshot. The structural controls are platform-specific and concrete: Android `FLAG_SECURE` on sensitive Activities (suppresses both screenshots and the Recents thumbnail) and a covering view on `onPause`; iOS overlaying or blurring the snapshot in `applicationWillResignActive` (or `sceneWillResignActive`); `android:importantForAutofill="no"` / iOS `isSecureTextEntry` and `textContentType` discipline on secret fields; `setInputType(TYPE_TEXT_FLAG_NO_SUGGESTIONS)` / disabling the keyboard cache on credential entry; and clearing or never copying secrets to the clipboard (iOS expiring `UIPasteboard` items). These are genuine on-device hardening, not a server-side-control proxy — but they protect the leak surface, not the secret's authority, which remains server-revocable.
- MAS mapping: MASVS-STORAGE-2, MASVS-PLATFORM-3

**Pattern: Sensitive data leaks to or via a third-party analytics/ad/crash SDK egressing in-process with the app's full privilege.**

- Severity: high (the `malicious_in_process_sdk` scale-vector loads — one over-broad or backdoored SDK across the install base reaches every user's `cached_pii_phi_on_device`, `stored_access_token`, and `advertising_id`; escalates to critical when the SDK has network plus storage plus reflection capability and the egress destination is unvetted)
- NIST: SC-7, SC-7(4), AC-4, AC-6, SR-3, SI-4
- Related concerns: non_repudiation (per-SDK collection and egress destination must be in the audit record and the privacy-manifest / Data-Safety declaration — routed there); privacy (PRIVACY-1/2 collection-and-consent face and the gap between declared and actual collection); integrity (an SDK that also ingests untrusted server responses is an inbound surface)
- Detail: MASVS-STORAGE-2 (data leaking out of the app) with the MASVS-PRIVACY collection face, the MASWE third-party-data-sharing / unnecessary-data-collection area, and CWE-359 Exposure of Private Personal Information. MASTG addresses it with the network-traffic-interception and SDK-data-flow analysis techniques (observe what the SDK reads in-process and where it ships it) and the privacy-manifest / Data-Safety cross-check. The boundary is `app_to_third_party_sdk`; the ATT&CK Mobile technique is in-process data collection and exfiltration over a network channel the app's own egress masks. The structural control is SDK capability scoping and provenance — SBOM and version pinning, a vetted egress allowlist, data-access minimization (no broad storage/identifier read), an iOS privacy manifest and Android Data Safety declaration that match actual collection, and consent gating before the SDK initializes. Because the SDK runs with the app's privilege, the only durable boundary is what data the app exposes to it and an egress destination allowlist — not a runtime check inside the same process.
- MAS mapping: MASVS-STORAGE-2, MASVS-PRIVACY-2; MASWE-0064

**Pattern: PII or tokens written to device logs (logcat / `os_log`), crash reports, or error output.**

- Severity: medium to high (high when `device_log_entry` carries a `stored_access_token`, credential, or PII/PHI — a co-resident app or a crash-reporting SaaS then reads it; medium where logging is verbose but non-sensitive; the audit-content sensitivity-inheritance rule applies — a log line carrying a token is token-sensitive)
- NIST: SI-11, AU-9, SC-28, AC-4
- Related concerns: non_repudiation (logs that double as the audit trail inherit the highest sensitivity of any field captured — routed there for content and access controls); ephemeral (log and crash-artifact retention); privacy (crash-report egress to a third-party crash SaaS is an SDK-egress concern, above)
- Detail: MASVS-STORAGE-1 (sensitive data persisted to logs) with the MASWE sensitive-data-in-logs area and CWE-532 Insertion of Sensitive Information into Log File. MASTG tests it with the logcat / unified-log inspection and crash-report content techniques. On Android the `co_resident_malicious_app` (or any reader of system logs on older OS / via `adb`) and on iOS the unified-log / sysdiagnose reader are the positions; a crash-reporting SDK egresses the report off-device. The structural control is release-build log suppression (strip debug logging at build, e.g. ProGuard/R8 log removal; gate on `BuildConfig.DEBUG` / `#if DEBUG`), field-level redaction of any sensitive value before it can reach a log or crash payload, and scrubbing tokens and PII from crash metadata before upload. Logging hygiene is on-device hardening of a leak surface; it does not change the secret's server-side authority.
- MAS mapping: MASVS-STORAGE-1; MASWE-0001

**Pattern: Cleartext or trust-all in-transit payload — HTTP, certificate validation disabled, a permissive trust manager / `NSAllowsArbitraryLoads`, or mixed content — on a credential- or PII-bearing channel.**

- Severity: critical (no transport encryption or disabled validation on a PII/token channel hits stock devices — the `network_mitm` position yields `stored_access_token` or `profile_pii` theft at scale with no rooted device required; the blast-radius pivots from one session to the backend, and reversibility on a stolen token is nil)
- NIST: SC-8, SC-8(1), SC-13, SC-23
- Related concerns: authenticity (certificate / public-key pinning is the verifiable-channel-identity layer — couples to the pinning capability and to identity-security for the protocol); integrity (a MitM that reads can also rewrite the response the client trusts); ephemeral (session-key lifetime on the channel)
- Detail: MASVS-NETWORK-1 (secure transport) with the MASWE cleartext-traffic / improper-certificate-validation area and CWE-319 Cleartext Transmission and CWE-295 Improper Certificate Validation. MASTG covers it with the network-traffic-interception technique (proxy with a user-installed CA), the cleartext-traffic test, and inspection of the Android Network Security Config and iOS App Transport Security exemptions. The ATT&CK Mobile technique is adversary-in-the-middle on the network path; the boundary is `client_to_backend_api`. The structural controls are a TLS floor (1.2 minimum, 1.3 preferred) with validated certificates, no `cleartextTrafficPermitted="true"` and no `NSAllowsArbitraryLoads` / per-domain ATS exceptions, no custom trust manager that accepts all certs, and no mixed content in any WebView. This is genuine on-device enforcement of an in-transit invariant — but pinning (Authenticity) and the server's own refusal to accept downgraded sessions are the corroborating layers; default platform TLS alone holds only against the casual on-path attacker, not a user-installed MitM CA.
- MAS mapping: MASVS-NETWORK-1; MASWE-0050

**Pattern: A WebView JavaScript bridge or an exported content provider leaks native data outward — the bridge hands on-device state to loaded web content, or an over-exposed provider serves sensitive rows to co-resident apps.**

- Severity: high (the `js_bridge_native_surface` and `deep_link_and_ipc_entry_points` crown jewels are reachable by untrusted web content or a `co_resident_malicious_app`; escalates when the bridge exposes file/storage/device APIs or the provider has no permission and serves tokens or PII, and when the WebView loads remote or attacker-influenced content)
- NIST: AC-3, AC-4, AC-6, SC-7, SC-18
- Related concerns: integrity (the same bridge and provider are inbound-untrusted-input surfaces — co-resident write / injected JS calling native — routed there; this file owns the outbound read); authenticity (origin allowlisting on the WebView and caller-identity verification on the provider); privacy (the leaked rows may be PII)
- Detail: MASVS-PLATFORM-2 (the WebView/IPC native-exposure face) with MASVS-PLATFORM-1 (component exposure), the MASWE insecure-WebView-configuration and exported-component areas, and CWE-749 Exposed Dangerous Method and CWE-927 Use of Implicit Intent / over-exported provider. MASTG tests it with the WebView and `addJavascriptInterface` / `WKScriptMessageHandler` analysis and the exported-component inspection techniques. The outbound leak crosses the `app_to_webview_js_bridge` and `app_sandbox_to_other_apps` boundaries; the ATT&CK Mobile technique is exploitation of an exposed inter-process surface to read app data. The structural control is bridge minimization and origin allowlisting — `WKWebView` with no `file://` access and a strict navigation/origin policy, `addJavascriptInterface` exposing only a minimal vetted surface to allowlisted origins (and never on a WebView loading remote content), `setAllowFileAccess(false)` / disabling mixed content, and exporting no content provider that serves sensitive rows (or gating it behind a signature-level permission and `android:exported="false"` where no cross-app access is intended). The bridge surface itself is the boundary; reducing it is real, but any data it exposes is data the device — and thus the attacker — can reach.
- MAS mapping: MASVS-PLATFORM-2, MASVS-PLATFORM-1

**Pattern: Weak or homegrown at-rest cryptography — ECB mode, a static/zero IV, a deprecated cipher (DES/3DES/RC4), or a key derived from a password without a KDF.**

- Severity: high (weak at-rest crypto over `cached_pii_phi_on_device` or a token store collapses to recoverable plaintext on a stolen or backed-up device — the protection is illusory; escalates when the same weak scheme is fleet-wide and a single recovered key unlocks every install's data)
- NIST: SC-13, SC-28, SC-28(1), SC-12, IA-5
- Related concerns: ephemeral (key derivation, rotation, and the KDF work-factor); integrity (an unauthenticated cipher mode lets a tamperer flip ciphertext — authenticated encryption couples the two goals); authenticity (where the key should be hardware-attested rather than software-derived)
- Detail: MASVS-CRYPTO-1 (the data-protection face — cryptographically secure algorithms and parameters) with the MASWE weak-cryptography / insecure-cipher-mode and weak-key-derivation areas, CWE-327 Use of a Broken or Risky Cryptographic Algorithm, CWE-329 Generation of Predictable IV, and CWE-916 Use of a Password Hash With Insufficient Computational Effort. MASTG covers it with the cryptography-configuration and key-management analysis techniques over the decompiled binary. The `reverse_engineer_with_ipa_apk` and `physical_thief_with_stolen_device` positions exploit it. The structural control is platform-vetted authenticated encryption (AES-GCM, never ECB; a unique random IV/nonce per encryption; no DES/3DES/RC4), keys generated in and never exported from the Android Keystore / iOS Keychain rather than derived in-app, and where a password-derived key is unavoidable a memory-hard KDF (Argon2id, scrypt, or PBKDF2 with a high iteration count and a random salt). Homegrown crypto on the client protects the leak surface only as well as its weakest parameter; the secret's authority must still be server-revocable.
- MAS mapping: MASVS-CRYPTO-1; MASWE-0020

**Pattern: Tech plan asserts "data is encrypted" or "secrets are stored securely" generically without specifying the at-rest substrate (Keystore/Keychain versus app storage), key non-exportability and hardware backing, the TLS floor and certificate-validation behavior, or which secrets reach the client at all.**

- Disposition: blocked or uncertainty
- prerequisite_evidence: "the on-device data inventory (every field from the mobile data taxonomy that is persisted) mapped to its storage substrate and whether the key is hardware-backed and non-exportable (Android Keystore/StrongBox vs `SharedPreferences`; iOS Keychain accessible-class / Secure Enclave vs `NSUserDefaults`); the at-rest cipher, mode, IV, and key-derivation policy; the TLS configuration (version floor, cipher allowlist, certificate-validation/pinning behavior, Network Security Config / App Transport Security exemptions); the third-party SDK inventory with each SDK's in-process data access and egress destinations against the privacy-manifest / Data-Safety declaration; and an explicit statement of which secrets, if any, ship in the binary versus are brokered server-side"

## Common capability patterns

**Pattern: All on-device secrets are held in a hardware-backed Keystore / Keychain (StrongBox / Secure Enclave where available) with non-exportable keys, and key release on sensitive material is biometric- or device-credential-gated.** Maturity ladder depends on evidence — designed when the tech plan names the Keystore/Keychain abstraction and asserts hardware backing; implemented when a config or code reference shows keys generated with `setIsStrongBoxBacked(true)` / `setUserAuthenticationRequired(true)` on Android or `kSecAttrTokenIDSecureEnclave` / a `LAContext`-gated `kSecAccessControl` on iOS, with the exportable/software-fallback path explicitly disallowed and backup excluded; tested when a report shows a rooted/jailbroken device cannot extract the key from process memory (no software fallback fired) and a `BiometricPrompt` / `LAContext` gate actually releases the key only on a fresh authentication; operationalized when key-attestation (key-attestation chain / Secure Enclave attestation) is verified server-side, biometric-enrollment-change invalidation is wired up, and a runbook covers key rotation and StrongBox-unavailable fallback policy. MAS mapping: MASVS-STORAGE-1, MASVS-CRYPTO-2 (control satisfied).

**Pattern: Sensitive screens suppress screenshots and the task-switcher snapshot and harden the clipboard and keyboard cache.** Maturity ladder depends on evidence — designed when the tech plan enumerates which screens are sensitive and asserts snapshot/clipboard hardening; implemented when code shows `FLAG_SECURE` on those Activities, an `applicationWillResignActive` / `sceneWillResignActive` cover-or-blur on iOS, `isSecureTextEntry` / `TYPE_TEXT_FLAG_NO_SUGGESTIONS` on secret fields, autofill disabled on credential entry, and no secret written to a non-expiring clipboard; tested when a report confirms the Recents thumbnail and a forced backgrounding snapshot are blank, the predictive-text store learns no typed secret, and a clipboard read by a second app returns nothing; operationalized when the sensitive-screen inventory is maintained as new screens ship and a lint/CI check flags a sensitive Activity missing `FLAG_SECURE`. MAS mapping: MASVS-STORAGE-2, MASVS-PLATFORM-3 (control satisfied).

**Pattern: The app enforces a TLS floor (1.2 minimum, 1.3 preferred) with validated certificates and no cleartext exemptions in the Android Network Security Config or iOS App Transport Security.** Maturity ladder depends on evidence — designed when the tech plan states the TLS floor and a no-cleartext intent; implemented when the Network Security Config shows `cleartextTrafficPermitted="false"` with no per-domain exception and the iOS `Info.plist` carries no `NSAllowsArbitraryLoads` / `NSExceptionAllowsInsecureHTTPLoads`, and no custom trust manager accepts all certificates; tested when an intercepting proxy with a user-installed CA fails to read traffic on the high-value channel (pinning, the Authenticity capability, is in evidence) and a cleartext-traffic scan returns nothing; operationalized when pin rotation and backup-pin strategy are documented, a pin-mismatch event is reported server-side, and the TLS policy is enforced in CI against config drift. MAS mapping: MASVS-NETWORK-1 (control satisfied).

**Pattern: Code obfuscation / anti-decompilation is applied as defense-in-depth behind a no-client-trusted-secret architecture.** This capability cross-cuts Authenticity (it raises reverse-engineering cost for the `reverse_engineer_with_ipa_apk` position) and is only ever a cost-raiser — it is scored as defense-in-depth, never as the control, and is meaningful only once the architecture has already established that no secret ships in the binary and every authorization and business rule is enforced server-side. Maturity ladder depends on evidence — designed when the tech plan names an obfuscator (R8/ProGuard with shrinking and name obfuscation, iOS symbol stripping / a commercial obfuscator) and explicitly states that no client-trusted secret exists behind it; implemented when the build configuration shows obfuscation and string/resource protection enabled on release builds with debug logging stripped; tested when a decompilation attempt confirms the symbol map and string table are meaningfully degraded and a static-analysis pass recovers no usable secret (because none is present); operationalized when obfuscation is enforced in the release pipeline, mapping files are retained for crash de-obfuscation under access control, and the architecture record states the server-side invariants this layer sits behind — making clear it delays the reverse engineer rather than stopping them. MAS mapping: MASVS-RESILIENCE-2 (control satisfied, defense-in-depth).
