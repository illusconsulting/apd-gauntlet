# Security tooling required-immutable data classes

For a platform that wields offensive capability or operates critical defensive functions, the following data classes must not change once written. Immutability findings test storage substrate, retention enforcement, deletion controls, and tamper-evidence against this list. The legal-defensibility overlay (CFAA, ROE, customer-MSA audit clauses) raises the bar above conventional API-domain immutability: mutability or deletion-by-single-credential on these classes is a presumption-of-misuse signal.

- **Operator-action audit log** — the chain-of-custody record distinguishing authorized testing from unauthorized intrusion under CFAA. Mutability or deletion-by-single-credential is a critical finding. Retention should match the longest applicable customer-MSA audit clause (commonly 3–7 years), the longest plausible legal-discovery window, and any regulatory anchor that applies (SOC 2 typically 1–7 years; NIS2 sectoral requirements).
- **Engagement-start records** — the ROE-attestation timestamp, target-inventory snapshot, and authorization-window declaration captured at the moment an engagement begins. This is the consent evidence on which the legal authorization of every subsequent command depends; without an immutable engagement-start record, every subsequent command is challengeable as out-of-scope.
- **Command-issued log** — every command sent to every implant, capturing operator, target implant, command-identifier (or command text), engagement reference, and issue-time. Required for after-action review, customer-deliverable provenance, and dispute resolution. Immutability prevents an operator from rewriting their own command history after the fact.
- **Result-harvest log** — the provenance record linking captured data to the implant and engagement that produced it (which implant captured which credential or screenshot at which time). Required for chain-of-custody if engagement results are ever used in a customer's own legal proceedings or regulatory disclosure.
- **Operator authentication events** — forensic evidence for operator-compromise reconstruction; retention should match or exceed operator credential lifetime plus the longest plausible detection window. NIST SP 800-53r5 AU-11 (Audit Record Retention) governs the floor.
- **Module / plugin install records** — supply-chain provenance for which plugin ran in the platform's privileged context when. Required for incident reconstruction when a plugin is later discovered malicious or backdoored; the install record links the source registry, version, signature-verification outcome, and dependency lockfile that were live at the time. Plugin removal MUST NOT erase prior-install records.
- **Signing-key lifecycle events** — creation, rotation, revocation, destruction events for c2_signing_key, plugin_signing_root, audit_log_signing_key, and listener_tls_intermediate_ca. Required for proving key-management discipline; required for incident scoping when a key is suspected compromised (the lifecycle record bounds when and which deployments are affected).
- **Customer-data-access log** — who in the operator team accessed which customer's data and when. Required at the multi-tenant boundary; the load-bearing audit class for cross-tenant abuse detection and customer-MSA reporting obligations.
- **Backup snapshots** — engagement archives frequently have regulatory or contractual retention obligations (customer MSAs commonly require 3–7 years of engagement-record retention; SOC 2 requires retention matching the service-organization policy). Object-lock with compliance mode or WORM media; mutability or deletion-by-single-credential is a critical finding given the legal-defensibility weight.
- **ROE document and engagement-scope definition history** — every version of every ROE for every engagement, with the activation and deactivation timestamps for each version. Required for proving which scope was in force when a given command was issued.
- **Plugin signature-verification outcomes** — every load-time signature check result (success and failure), retained for the lifetime of the audit retention. Required for proving that a backdoored plugin would have been rejected at the time it was loaded (or, conversely, for proving the signature-verification step was bypassed or failed open).
- **Cross-tenant access attempts** — including denied attempts. Insider-threat signal; the absence of a record of denial is itself a finding because it implies either no attempt occurred or no detection exists.
- **Audit-of-audit events** — operator queries and exports of the audit log itself. Required for separation-of-duties enforcement at the audit boundary; an operator who can read the audit log undetectably can plan around their own actions.

Specialists raise Immutability findings against any class on this list that has mutable storage, absent retention controls, deletion-by-single-credential, or unspecified retention. The synthesizer cross-references Non-Repudiation findings on the same data class so the merged record carries both concerns. For security-tooling specifically, the synthesizer also cross-references Authenticity findings on the signing material protecting these immutable classes — an immutable log signed by a key with weak custody is operationally as bad as a mutable log.
