# Extending Agents

This guide is for framework contributors who want to modify agents, skills, or schemas — not for authors of new domain packs (see [adapting-to-other-domains.md](adapting-to-other-domains.md) for that).

## When to modify a specialist agent

The nine specialist agents (`apd-confidentiality.md` through `apd-immutability.md`) have a stable structure:

```
---
name: apd-<goal>
description: ...
---

# <Goal> Specialist (Tier N, <Tier Name>)

## Required reading
1. ... <list of skill files>

## Inputs and output
...

## Analytical checklist
### <topic>
- analytical question
- analytical question

## Boundary watch
...

## Common patterns
... <pointer to apd-domain skill>

## Self-check before emitting
1. ...
```

Each lens agent's Required reading list includes a **per-goal domain sidecar** — `.claude/skills/apd-domain/by-goal/<goal>.md` — rather than the full cross-goal `SKILL.md`. The sidecar contains the four calibration files (severity rubric, consequential actions, immutability classes, data taxonomy), the merged domain surfaces, and only that goal's common patterns, plus a `pruned` manifest; this bounds each agent's context to what it actually needs (~44% reduction at three packs). The full cross-goal `SKILL.md` is retained for non-lens agents (intake, attack-path-analyzer, domain-auditor).

Sidecars are generated by `build-domain-skill` alongside the full skill; do not hand-edit them. To suppress sidecar generation, pass `--full-only`.

You typically want to modify a specialist when:

- A new analytical pattern emerges in the lens (e.g., a new attack technique becomes industry-relevant). Add it to the Analytical Checklist.
- A boundary call between adjacent goals needs adjustment. Update the Boundary watch section. Also update `apd-framework/SKILL.md` if the call is now framework-wide.
- A common pattern is broadly applicable across domains. This usually means it's a *framework* pattern; modify the agent, not the domain pack.

If a pattern is PBM-specific, modify `domains/pbm/common-patterns/<goal>.md` instead.

## When to modify a skill

| Skill | Modify when |
|---|---|
| `apd-framework` | Lens definitions or boundary calls between goals change |
| `apd-finding-schema` | Schema contracts change (and update the JSON Schemas in `schemas/`) |
| `apd-evidence-discipline` | The five discipline rules or maturity discipline change |
| `apd-control-mappings` | NIST family guidance or MITRE crosswalk convention changes |
| `apd-domain` | **Never edit by hand** — it's generated by `apd-gauntlet build-domain-skill`. This includes the full cross-goal `SKILL.md` and the per-goal sidecars under `.claude/skills/apd-domain/by-goal/<goal>.md` (suppress sidecars with `--full-only`). |

After modifying any skill, run `apd-gauntlet lint-agents` to verify Required reading references still resolve.

## When to modify a schema

This is the most disruptive change category. Schema modifications are governed by [schema-evolution.md](schema-evolution.md).

Workflow:

1. Update the JSON Schema in `schemas/<kind>.schema.json`.
2. Add positive and negative test fixtures in `tests/fixtures/{valid,invalid}/` that exercise the new constraint.
3. Update the test driver if needed (`tests/test_finding_schema.py`, etc.).
4. Update `apd-finding-schema/SKILL.md` to document the change (the skill is the human-readable companion; the schema is the canonical contract).
5. Update the relevant template at `templates/<kind>.template.yaml`.
6. Update the bundled example in `examples/` to match.
7. Bump `schema_version` in the schema's `const` value if the change is breaking.
8. Bump the framework version per [schema-evolution.md](schema-evolution.md).
9. Update `CHANGELOG.md`.

## When to add a new validator lint

The validator has three passes (schema, semantic, cross-file). Adding a new check:

1. Decide which pass it belongs in:
   - **Schema pass** if the constraint can be expressed declaratively.
   - **Semantic pass** if it's a single-record check (token count, deterministic ID, etc.).
   - **Cross-file pass** if it needs the intake brief or cross-record state.
2. For semantic lints: add the function to `tools/apd_gauntlet/linters.py`; wire it into `run_semantic_pass` in `validate.py`.
3. For cross-file lints: extend `run_cross_file_pass` in `validate.py`.
4. Add a fixture-driven test in `tests/test_validate_semantic.py` or `tests/test_validate_cross_file.py`.
5. Verify coverage stays ≥ 85% on `tools/apd_gauntlet/`.

Don't grow the validator into a "lint everything" tool. The bar for a new lint: it catches a class of issues that has shown up in real runs. If it's hypothetical, defer.

## When to add a new CLI command

The CLI surface is intentionally narrow (8 commands). Add a new command only if:

- It serves a workflow that the existing commands can't cover.
- It's small enough to fit on one screen of help output.
- It will be used routinely (not just once at setup).

Workflow:

1. Add a module under `tools/apd_gauntlet/` (e.g. `tools/apd_gauntlet/new_command.py`) with the business logic.
2. Wire it into `tools/apd_gauntlet/cli.py` with a Click decorator.
3. Add a fixture-driven test in `tests/test_<command>.py`.
4. Update `docs/running-the-gauntlet.md` if it's operator-facing.

## When to add a new specialist agent

Adding a tenth specialist is a major version change. It implies:

- Defining a new APD goal (which would break the three-tier × three-goal symmetry).
- Updating all schemas to add the new agent prefix.
- Cross-tier dependency rules (which tier?).
- All existing specialists may need updated boundary calls.

This is intentionally hard to do — the framework's nine-goal structure is part of its identity. If you find a concern that doesn't fit existing lenses, first check the boundary calls in `apd-framework/SKILL.md`; usually one of the existing nine goals is the right home.

## When to add an activation-gated optional agent

The framework's nine-goal symmetry is closed, but new *cross-cutting* analyses that consume the deduped specialist outputs (or that enrich the intake) do not require a new goal. These are added as **activation-gated optional agents**: they sit at tier 0 (intake-enrichment) or tier 4 (synthesis-augmentation), the orchestrator dispatches them only when their preconditions are met, and they emit a finding-prefix the synthesizer recognizes.

The optional agents already in v1.x follow this pattern (one always-on tier-0 context-builder, `apd-threat-model-author`, is listed alongside them for completeness — it runs on every run rather than on a precondition):

| Agent | Tier | Activation precondition | Output prefix |
|---|---|---|---|
| `apd-code-recon` (v1.1+) | Tier 0 | `code_recon` enabled and codebase-memory-mcp reachable | enriches intake (`00-context/code-evidence-index.yaml`) |
| `apd-threat-model-author` (v1.6+) | Tier 0 | Always-on — runs every run (no precondition) | authors the canonical intake baseline (`00-context/threat-model-normalized.yaml` + `00-context/threat-model-authored.md`) |
| `apd-threat-model-recon` (v1.3+) | Tier 0 | `threat_model:` path declared in run-config (or a TM-like artifact detected) | enriches intake (`00-context/threat-model-supplied-normalized.yaml` — the supplied sibling; the author owns the canonical file) |
| `apd-threat-model-evaluator` (v1.3+) | Tier 4 | Normalized threat model exists (now always — the author's baseline is always present) | `tmeval-*` findings |
| `apd-attack-path-analyzer` (v1.4+) | Tier 4 | At least one crown jewel and at least one attacker position declared (domain pack or run-config) | `apath-*` findings |

The `apd-attack-path-analyzer` is the canonical worked example. It demonstrates the full pattern: (1) declare activation preconditions in the active domain pack with run-config override; (2) emit a `*-skipped.txt` artifact when preconditions are unmet; (3) emit a `disposition: blocked` finding when the operator's explicit declaration contradicts the domain default; (4) write its discipline rules to a dedicated skill file the agent declares as required reading; (5) extend `finding.schema.json` additively with a new `agent` enum value and a new id prefix pattern.

Workflow for adding a new activation-gated agent:

1. **Decide tier.** Tier 0 if the agent enriches intake; tier 4 if it consumes specialist outputs.
2. **Author the agent file** under `.claude/agents/apd-<name>.md`. Use the existing `apd-attack-path-analyzer` as a structural template — frontmatter, Required reading, Inputs and output, Discipline, Self-check.
3. **Author the discipline skill** under `.claude/skills/apd-<name>-discipline/SKILL.md` parallel to `apd-attack-path-discipline` and `apd-threat-model-methodologies`. The discipline skill captures the never-invent rules, confidence floors, and emit/block decisions specific to the agent's analysis.
4. **Extend `finding.schema.json` additively.** Add the new agent name to the `agent` enum; extend the `id` pattern with a new prefix; mirror the extension on `cross_references` and `merged_from`. Bump the framework version but not the schema_version (additive change).
5. **Wire activation into the orchestrator.** Document the activation table in the agent's operator doc (e.g., `docs/attack-path-analysis.md`). The orchestrator dispatches when the precondition table evaluates to "run"; emits a skip artifact when it evaluates to "skipped silently"; or emits a `disposition: blocked` finding when it evaluates to "blocked".
6. **Write the operator doc** at `docs/<feature>.md` and link it from `docs/architecture.md` (the agents table and the topology list), from `docs/running-the-gauntlet.md` (a peer section to "Code reconnaissance" and "Threat model evaluation"), and from this guide (the activation-gated-agent worked-example table above).
7. **Add a test stub** asserting the agent file lints clean (`tests/test_lint_agent_apd_<name>.py`) and the discipline skill file lints clean (`tests/test_skill_apd_<name>_discipline.py`).

## Testing changes

Every change should:

- Pass `pytest`.
- Pass `ruff check tools/ tests/` and `mypy tools/`.
- Validate `apd-gauntlet validate examples/apd-20260601-claim-event-bus/expected/` cleanly. If your change requires the example to change, update both atomically.
- For agent/skill changes: pass `apd-gauntlet lint-agents`.

The CI workflows enforce these gates on every PR.
