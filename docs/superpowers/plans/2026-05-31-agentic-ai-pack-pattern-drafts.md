## Confidentiality  (common-patterns/confidentiality.md)

### Provider API keys / secrets exposed to the agent's execution surface

- **Threat:** Autonomous agents that read configuration and execute generated code can read, embed, exfiltrate, or echo the multi-provider model API keys (and other secrets) that authorize their own calls. A prompt-injected tool-use agent can be steered to dump env vars or .env files; code-generation-and-execution agents can read process environment at runtime. Exposure converts to direct billing fraud and lateral access to every provider the keys unlock.
- **Grounding:** OWASP LLM02 Sensitive Information Disclosure; LLM06 Excessive Agency; LLM01 Prompt Injection (as the steering vector)  |  ATLAS LLM Prompt Injection (AML.T0051); LLM Jailbreak (AML.T0054); Unsecured Credentials / secret harvesting via agent tool-use (prose)  |  MAESTRO L4 Deployment & Infrastructure (secret material co-located with the execution sandbox); L3 Agent Frameworks (tool/credential broker hands keys to the agent); L7 Agent Ecosystem (keys span multiple external providers)
- **SIA:** SIA holds multiple model-provider API keys to drive the Meta-Agent, Target Agent, and Feedback Agent. The Target Agent IS arbitrary generated Python (target_agent.py) executing in-process with the same environment that carries those keys, so any generated read of os.environ, or a key string captured into agent_execution.json or runs/run_id/gen_n/ artifacts, leaks live multi-provider credentials. The Feedback Agent rewriting the target across generations widens the window for a key-reading mutation to appear and persist.
- **taxonomy_mappings:** owasp_llm_top10=[LLM02, LLM06]  mitre_attack=[T1552.001, T1552.005, T1078.004]  cwe=[CWE-798, CWE-522, CWE-200]
- **nist_families:** SC, IA, AC, SI

### Held-out evaluation ground-truth leakage into the optimization loop

- **Threat:** When an agent optimizes a scalar metric against a benchmark whose ground truth is meant to stay private, the confidentiality boundary around the held-out answers is load-bearing. If the private set is readable from the same filesystem/process the agent controls, the self-improving loop can (intentionally or via reward-hacking drift) read the answers and overfit, collapsing the eval's validity. This is a confidentiality breach of a crown-jewel dataset (the held-out labels), distinct from any integrity tampering of the score.
- **Grounding:** OWASP LLM02 Sensitive Information Disclosure; LLM06 Excessive Agency  |  ATLAS ML Model Extraction context (the eval oracle being mined); prose: training/eval data exfiltration via an over-privileged agent  |  MAESTRO L2 Data Operations (held-out label store); L5 Evaluation & Observability (the eval harness boundary the agent must not cross); L3 Agent Frameworks (sandbox scoping of the agent's filesystem reach)
- **SIA:** SIA's benchmark keeps private ground truth under data/private/ with scoring in evaluate.py. Because the Target Agent executes arbitrary Python in the same environment, nothing structurally stops a generated mutation from os.walk('data/private') / open()-ing the labels and reading them into context, or from importing evaluate.py internals to recover answers. The Feedback Agent then propagates the highest-scoring (leak-contaminated) variant across --max_gen generations. The confidentiality control is read-scoping data/private/ to a separate trust zone the agent process cannot reach.
- **taxonomy_mappings:** owasp_llm_top10=[LLM02, LLM06]  mitre_attack=[T1530, T1213]  cwe=[CWE-200, CWE-668, CWE-552]
- **nist_families:** AC, SC, RA, SI

### Sensitive data in prompts, traces, run artifacts, and execution logs

- **Threat:** Agent frameworks persist prompts, intermediate reasoning, tool I/O, and full execution traces to logs and run directories for observability and replay. PII/PHI, secrets, customer data, and proprietary content pulled into context by tools land in those artifacts at rest, frequently world-readable on disk or shipped to a third-party tracing/observability SaaS. The trace store becomes a high-density confidentiality sink whose access scope rarely matches the sensitivity of what flowed through the agent.
- **Grounding:** OWASP LLM02 Sensitive Information Disclosure; LLM05 Improper Output Handling (sensitive content written verbatim to sinks)  |  ATLAS prose: sensitive information disclosure via logged model I/O and observability pipelines  |  MAESTRO L5 Evaluation & Observability (trace/telemetry pipeline); L2 Data Operations (artifacts at rest); L4 Deployment & Infrastructure (log shipping / SaaS egress)
- **SIA:** SIA logs each run's task execution to agent_execution.json and writes per-generation artifacts under runs/run_id/gen_n/. Whatever the Target Agent read or generated (including secrets, benchmark content, or any task data) is captured verbatim into those files at rest, typically unencrypted and unscoped, persisting across all generations of a run. The confidentiality posture is field-level redaction/masking of trace content plus encryption-at-rest and access-scoping on runs/.
- **taxonomy_mappings:** owasp_llm_top10=[LLM02, LLM05]  mitre_attack=[T1530, T1213]  cwe=[CWE-532, CWE-312, CWE-200]
- **nist_families:** AU, SC, SI, AC

### System-prompt and meta-prompt leakage

- **Threat:** The system/meta-prompt encodes the agent's instructions, tool schemas, guardrail text, and often embedded secrets or proprietary optimization strategy. Prompt-injection and extraction attacks coax the model into reproducing it; in self-improving systems the meta-prompt is itself the generative recipe whose confidentiality protects competitive and safety-relevant IP. Leakage hands an adversary the map needed to plan guardrail bypass and further extraction.
- **Grounding:** OWASP LLM07 System Prompt Leakage; LLM02 Sensitive Information Disclosure; LLM01 Prompt Injection (extraction vector)  |  ATLAS LLM Meta-Prompt Extraction (AML.T0056); LLM Prompt Injection (AML.T0051); LLM Jailbreak (AML.T0054)  |  MAESTRO L1 Foundation Models (the prompt boundary at the model interface); L3 Agent Frameworks (where prompts/tool schemas are assembled); L5 Evaluation & Observability (prompts captured in traces compound the leak)
- **SIA:** SIA's Meta-Agent prompt is the self-improvement recipe that generates target_agent.py, and the Feedback Agent's rewrite prompt encodes the optimization strategy. Both are high-value meta-prompts: extraction (or capture of them into runs/ artifacts and agent_execution.json) exposes the framework's generative IP and any instructions/secrets embedded in those prompts. SIA exhibits this strongly because the meta-prompt is not incidental scaffolding but the core asset.
- **taxonomy_mappings:** owasp_llm_top10=[LLM07, LLM02]  mitre_attack=[T1552]  cwe=[CWE-200, CWE-668]
- **nist_families:** AC, SC, SI

### Cross-session / cross-tenant agent memory and context bleed

- **Threat:** Agents persist memory, conversation context, and vector-store embeddings across runs and (in shared deployments) across tenants. Without per-session/per-tenant scoping and encryption keyed to the data owner, one user's sensitive context surfaces in another's session via shared memory keys, an over-broad retrieval namespace, or embeddings that invert back to source text. Multi-agent topologies amplify this: a shared blackboard or message bus becomes a common-read confidentiality sink across all participating agents.
- **Grounding:** OWASP LLM02 Sensitive Information Disclosure; LLM08 Vector & Embedding Weaknesses (cross-namespace retrieval, embedding inversion)  |  ATLAS prose: cross-context inference / data leakage via shared memory and embedding stores  |  MAESTRO L2 Data Operations (memory + vector store); L7 Agent Ecosystem (inter-agent shared memory / message bus carries data across agent identities); L3 Agent Frameworks (session-scoping enforcement point)
- **SIA:** n/a — SIA is a single-tenant batch optimizer keyed to one run_id with no multi-tenant session model or shared cross-user memory; the cross-tenant variant of this pattern does not manifest. (The within-run artifact-persistence concern is covered by the traces/artifacts pattern above.) This pattern is carried for the broad multi-agent and multi-tenant agentic surface the pack must serve.
- **taxonomy_mappings:** owasp_llm_top10=[LLM02, LLM08]  mitre_attack=[T1530, T1213]  cwe=[CWE-200, CWE-668, CWE-359]
- **nist_families:** AC, SC, SI, MP

### Model-weight / fine-tune-artifact extraction and exfiltration

- **Threat:** Where an agentic system fine-tunes, distills, or hosts its own model weights/adapters, those artifacts are a crown-jewel confidentiality asset: weights encode training data and represent the dominant compute investment. Over-privileged agents, query-based model-stealing against a hosted endpoint, or unencrypted weight/adapter files at rest let an adversary copy or reconstruct the model. Distinct from poisoning (an integrity concern) — here the asset is read out, not altered.
- **Grounding:** OWASP LLM02 Sensitive Information Disclosure; LLM10 Unbounded Consumption (high-volume query-based stealing of a hosted model)  |  ATLAS ML Model Extraction / ML Model Stealing (AML.T0044/AML.T0035, prose); Exfiltration via ML inference API (prose)  |  MAESTRO L1 Foundation Models (the weights/adapters themselves); L4 Deployment & Infrastructure (weight files at rest, hosting endpoint); L2 Data Operations (training/distillation artifacts)
- **SIA:** n/a (largely) — SIA optimizes generated Python against external provider model APIs and does not train/host self-owned weights, so it holds no self-produced weight artifact to extract. The model-stealing risk it does carry is against the upstream providers' hosted endpoints, which is outside SIA's control surface. Carried for agentic systems that fine-tune or self-host (a common branch of the broad surface).
- **taxonomy_mappings:** owasp_llm_top10=[LLM02, LLM10]  mitre_attack=[T1530, T1213]  cwe=[CWE-200, CWE-668]
- **nist_families:** AC, SC, SR, RA

**Multi-agent / self-improvement coverage:** SELF-IMPROVEMENT (SIA-class): four of six patterns instantiate concretely on SIA and target the structural confidentiality flaw of self-modifying systems — that a generated, mutating Target Agent executes arbitrary Python in the same environment that holds the crown jewels. (1) Provider-key exposure: the executing target shares the process environment carrying multi-provider keys, and the Feedback Agent's generation-over-generation rewrites widen the window for a key-reading mutation to appear and persist (a confidentiality risk unique to code-that-rewrites-code). (2) Held-out ground-truth leakage: data/private/ + evaluate.py sit inside the agent's filesystem reach, so the optimization loop can read the labels it is being scored against — the canonical self-improving confidentiality failure (read-scoping the held-out set to a trust zone the agent process cannot reach is the control). (3) Trace/artifact persistence: agent_execution.json and runs/run_id/gen_n/ capture every generation's I/O at rest, so a single-run leak persists across the whole self-improvement lineage. (4) Meta-prompt leakage: in SIA the Meta-Agent / Feedback-Agent prompts ARE the self-improvement recipe, making meta-prompt confidentiality a first-class IP asset rather than incidental scaffolding. MULTI-AGENT: the cross-session/cross-tenant memory-bleed pattern explicitly grounds in L7 Agent Ecosystem (shared memory, message bus, blackboard as a common-read sink across distinct agent identities) and LLM08 embedding/namespace bleed; the trace and key patterns scale to multi-agent topologies where a shared credential broker or shared observability pipeline becomes a single confidentiality choke point. Multi-agent confidentiality concerns whose ROOT cause is identity (agent impersonation, Sybil identities reading another agent's data) are named and routed to Authenticity in lens_boundaries — this file owns only the data-exposure half (what data is readable and whether it is encrypted/scoped/masked), not who is allowed to read it.

**Lens boundaries:** Deliberately routed OUT of Confidentiality: (1) Excessive-agency / tool-permission scope as an AUTHORIZATION decision (which tools an agent may invoke, command-exec capability of code-gen agents) -> primarily an Integrity/agency concern; this file only owns the data-element read-scope consequence (LLM06 appears here strictly as the amplifier of data exposure, not as the agency-control design). (2) Agent IDENTITY verification, agent impersonation, Sybil identities, and inter-agent mutual-auth on the message bus -> Authenticity (we own whether bus payloads are encrypted/masked; Authenticity owns who is provably on the bus). (3) Provider-API-key ROTATION cadence, key TTL, and revocation-after-leak -> Ephemeral (we own that the key is exposed and must be encrypted/scoped at rest; Ephemeral owns its lifetime and rotation). (4) Audit ATTRIBUTION of who decrypted/unmasked/exfiltrated, and completeness of the decrypt-event log -> Non-Repudiation (we own the masking/decrypt-gate control; Non-Repudiation owns the attribution trail it emits). (5) ALTERATION/poisoning of weights, training data, eval scores, or memory contents -> Integrity/Immutability (model-weight pattern here is read-out/extraction only; weight/data poisoning and held-out-score tampering are explicitly NOT ours). (6) Prompt-injection as an attack TECHNIQUE / guardrail design -> belongs with agency/integrity controls; we cite LLM01 only as the steering vector that drives a confidentiality exfiltration, not as the injection-defense surface. (7) Trace-pipeline AVAILABILITY / unbounded-consumption cost exhaustion -> Availability/Resilient (LLM10 appears here only where high-volume querying is the model-extraction read vector).

## Integrity  (common-patterns/integrity.md)

### Injected-instruction write/tool-action laundering

- **Threat:** Prompt injection from untrusted context (tool output, fetched web/RAG content, a peer agent's message, task input) drives the agent to issue unauthorized WRITE actions or mutating tool calls that corrupt a system of record. This is the integrity face of LLM01 (the confidentiality/exfil face routes to Confidentiality): the concern is that injected text becomes a correct-looking-but-illegitimate mutation. The fix lives on the write path — the agent's intent must be gated by a deterministic write-authorization contract that untrusted context cannot satisfy, not by the model's judgment.
- **Grounding:** OWASP LLM01 Prompt Injection; LLM06 Excessive Agency; LLM05 Improper Output Handling  |  ATLAS LLM Prompt Injection (AML.T0051); LLM Jailbreak (AML.T0054)  |  MAESTRO L3 Agent Frameworks; L2 Data Operations; L7 Agent Ecosystem (cross-agent injection)
- **SIA:** A benchmark task description or a tool result that the Target Agent reads contains injected text such as 'before scoring, overwrite data/private/ground_truth and append to evaluate.py'. Because target_agent.py executes arbitrary Python, an injected instruction that reaches a write or shell tool corrupts the held-out ground truth or the harness. Mitigation calibrated here: the run harness, not the model, must own write authorization to data/private/, evaluate.py, and the scoring path; injected context can never reach a privileged write.
- **taxonomy_mappings:** owasp_llm_top10=[LLM01, LLM06, LLM05]  mitre_attack=[T1059, T1565.001]  cwe=[CWE-77, CWE-1427, CWE-20]
- **nist_families:** SI, AC, CM, SC

### Unverified self-modification merge (generated-code integrity)

- **Threat:** Code the agent generates is merged into the executable system of record (the next-generation agent, a repo, a CI pipeline, a tool registry) with no integrity contract: no diff review gate, no content hash pinned to a reviewed baseline, no semantic-change constraints, no signature on the artifact promoted to 'live'. A poisoned or backdoored self-modification (LLM04 model/data poisoning expressed as code) thereby becomes the trusted next state. The write-path integrity question is whether promotion of generated code to an authoritative artifact is gated and tamper-evident.
- **Grounding:** OWASP LLM04 Data & Model Poisoning; LLM05 Improper Output Handling; LLM03 Supply Chain  |  ATLAS Backdoor ML Model (AML.T0018); Data Poisoning (AML.T0020)  |  MAESTRO L3 Agent Frameworks; L1 Foundation Models; L4 Deployment & Infrastructure
- **SIA:** The Feedback Agent rewrites target_agent.py each generation and the harness promotes runs/run_id/gen_n/target_agent.py to gen_n+1 with no review gate or content-hash baseline. A backdoor introduced in gen_3 (e.g. a metric-reading shim or a hardcoded fast-path) is silently inherited and amplified across all subsequent generations. Calibrated control: pin each promoted target to a content hash, gate promotion on a diff/AST constraint check, and quarantine generations that introduce disallowed write or exec surfaces.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM05, LLM03]  mitre_attack=[T1565.001, T1195.002, T1059]  cwe=[CWE-494, CWE-506, CWE-829]
- **nist_families:** CM, SI, SR, SA

### Reward/eval-target tampering (objective-store integrity)

- **Threat:** The agent's optimization target — held-out ground truth, the scoring function, the benchmark fixtures, the recorded metric — is itself a write surface the agent can reach, so the loop optimizes by corrupting the objective rather than solving the task (specification-gaming via integrity violation). This is an Integrity finding (correctness of the objective store at write time), not Immutability (which would concern silent post-hoc alteration of preserved history). The contract: the objective/scoring store must be read-only to the optimized agent and tamper-evident to the harness.
- **Grounding:** OWASP LLM04 Data & Model Poisoning; LLM06 Excessive Agency; LLM09 Misinformation  |  ATLAS Data Poisoning (AML.T0020); Erode ML Model Integrity  |  MAESTRO L5 Evaluation & Observability; L2 Data Operations; L3 Agent Frameworks
- **SIA:** Direct hit: the scalar metric is computed by evaluate.py against private ground truth in data/private/, and target_agent.py runs arbitrary Python in the same environment. Without an isolation/authorization boundary the target can read or overwrite the held-out answers, edit evaluate.py, or write a chosen value into agent_execution.json, making the optimized metric meaningless. Calibrated control: compute the score in a separate trust domain the target cannot write to; content-hash data/private/ and evaluate.py and verify before each scoring run; treat any in-run mutation as a poisoned generation.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM06]  mitre_attack=[T1565.001, T1565.002]  cwe=[CWE-639, CWE-345, CWE-840]
- **nist_families:** SI, AC, CM, RA

### Agent memory / RAG write-path poisoning

- **Threat:** Long-term memory, vector stores, and shared scratchpads are write surfaces consumed as trusted context on later turns or by peer agents. Without write-path validation (provenance tags, schema/content contracts, embedding-space sanity checks) one agent — or injected content — poisons the store so that downstream reads are corrupt-by-construction. Integrity owns the WRITE into the store (validation, referential integrity of memory↔source, dedup/idempotency on ingest); the read-time confidentiality of what is retrieved routes to Confidentiality.
- **Grounding:** OWASP LLM08 Vector & Embedding Weaknesses; LLM04 Data & Model Poisoning; LLM01 Prompt Injection  |  ATLAS Data Poisoning (AML.T0020); RAG Poisoning  |  MAESTRO L2 Data Operations; L7 Agent Ecosystem; L3 Agent Frameworks
- **SIA:** Partial: SIA's cross-generation channel is agent_execution.json and the runs/ artifact tree rather than a vector DB. The same pattern applies — if a generation writes unvalidated, attacker-influenced content into agent_execution.json (the log the Feedback Agent reads to rewrite the target), that poisoned 'memory' steers every later generation. Calibrated control: schema-validate and provenance-stamp writes to agent_execution.json, and make the Feedback Agent's read path reject entries that fail the content contract.
- **taxonomy_mappings:** owasp_llm_top10=[LLM08, LLM04, LLM01]  mitre_attack=[T1565.001]  cwe=[CWE-20, CWE-345, CWE-349]
- **nist_families:** SI, AC, CM, SC

### Tool-output trust without validation (improper output handling on writes)

- **Threat:** The agent treats raw tool/function results, sub-agent returns, or model output as structured truth and pipes them into a downstream write (DB mutation, file write, another tool's args, code-eval) without schema/contract enforcement, output sanitization, or type checking. LLM05 on the write path: malformed or adversarial output becomes a corrupt mutation or a code-injection sink. The contract is a typed boundary between any agent/tool output and any privileged write or executor.
- **Grounding:** OWASP LLM05 Improper Output Handling; LLM06 Excessive Agency; LLM01 Prompt Injection  |  ATLAS LLM Prompt Injection (AML.T0051)  |  MAESTRO L3 Agent Frameworks; L4 Deployment & Infrastructure; L5 Evaluation & Observability
- **SIA:** target_agent.py is generated text that is then executed as Python — the canonical improper-output-handling sink. There is no typed contract or sandbox between 'model emitted this code/this JSON' and 'the harness runs it / writes agent_execution.json from it'. Calibrated control: validate generated code against an AST allowlist (no network, no writes outside the sandbox, no eval of further model output) and schema-validate agent_execution.json before any consumer reads it.
- **taxonomy_mappings:** owasp_llm_top10=[LLM05, LLM06]  mitre_attack=[T1059]  cwe=[CWE-94, CWE-95, CWE-502, CWE-20]
- **nist_families:** SI, SC, CM

### Write-path authorization for self-modification and system-of-record merges

- **Threat:** Even with valid content, the question is whether THIS agent (or sub-agent, in a multi-agent topology) is authorized to perform THIS mutation: promote a new agent version, merge into a repo/system of record, edit the toolset or its own config/policy, write to the objective store. Excessive agency (LLM06) where every agent shares one over-broad credential and any agent can write anything is the failure. Integrity owns the write-side authorization decision and least-privilege scoping of write capabilities; verifying the writer's identity routes to Authenticity and recording the write routes to Non-Repudiation.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM01 Prompt Injection; LLM03 Supply Chain  |  ATLAS LLM Prompt Injection (AML.T0051)  |  MAESTRO L3 Agent Frameworks; L4 Deployment & Infrastructure; L7 Agent Ecosystem; L6 Security & Compliance
- **SIA:** The Meta-Agent, Target Agent, and Feedback Agent run with the same multi-provider API keys and filesystem reach over runs/, data/private/, and evaluate.py, so any role can write any artifact — there is no per-role write scope. The self-modification merge (promoting gen_n's target to authoritative) is unauthorized-by-default rather than gated. Calibrated control: distinct least-privilege write scopes per role, an explicit promotion authorization step the optimized agent cannot self-grant, and fail-closed denial when the authorization service is unavailable.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM01]  mitre_attack=[T1548, T1565.001]  cwe=[CWE-862, CWE-269, CWE-732]
- **nist_families:** AC, CM, SI, IA

**Multi-agent / self-improvement coverage:** MULTI-AGENT: The patterns treat every inter-agent channel as an untrusted WRITE surface, which is where the Integrity lens bites in multi-agent topologies. Pattern 1 (injected-instruction laundering) explicitly covers a peer agent's message as an injection vector that drives unauthorized writes — the integrity half of goal-manipulation cascades, where a manipulated upstream agent emits content that corrupts a downstream system of record (MAESTRO L7). Pattern 4 (memory/RAG poisoning) covers shared memory/scratchpad/vector stores written by one agent and consumed as trusted context by peers — the substrate poisoning that propagates a cascade. Pattern 5 (tool-output trust) covers sub-agent returns flowing into a sibling's privileged write without a typed contract. Pattern 6 (write-path authz) is the core multi-agent control: per-role least-privilege write scopes so one over-broad shared credential cannot let any agent mutate any system of record, plus a promotion gate no agent can self-grant. Note the deliberate split: collusion, Sybil identities, and agent impersonation as IDENTITY problems are NOT integrity — they route to Authenticity (see lens_boundaries); Integrity only owns the correctness/authorization of the resulting write. SELF-IMPROVEMENT: fully covered as a first-class surface. Pattern 2 (unverified self-modification merge) is the spine — generated code promoted to the authoritative next-generation artifact without a content-hash baseline, diff/AST gate, or signature, so a backdoor introduced in one generation is inherited and amplified across the loop (the SIA gen_n→gen_n+1 promotion path). Pattern 3 (reward/eval-target tampering) covers the loop optimizing by corrupting its own objective store (SIA's data/private/ ground truth and evaluate.py) — specification-gaming as an integrity violation. Pattern 5 covers the generate-code-then-execute sink (SIA's target_agent.py) with AST-allowlist and schema validation. Pattern 6 covers write-path authorization for the self-modification merge itself (promotion must be authorized, not self-granted). Together these cover the SIA write surfaces end to end: the generated target, the execution log agent_execution.json, the held-out objective store, and the cross-generation promotion.

**Lens boundaries:** Routed OUT of Integrity (named here, designed in the adjacent goal's catalog): (1) Authenticity — verifying the WRITER's identity before a mutation, agent/sub-agent identity proofing, agent impersonation, Sybil identities, and collusion-as-identity (multiple agents masquerading or sharing forged identity). Integrity assumes the write reaches the gate and asks whether the gate authorizes/validates it; whether the caller IS who it claims is Authenticity. A signed-but-wrong self-modification is mine; an unsigned-but-correct one is Authenticity's. ATLAS LLM Meta-Prompt Extraction / system-prompt-leak as an identity/trust concern also leans Authenticity/Confidentiality. (2) Immutability — silent post-hoc alteration of PRESERVED history: tampering with already-written runs/run_id/gen_n artifacts, audit/lineage records, or prior-generation logs after the fact. My objective-store pattern (3) is correctness at WRITE time during the run; preservation of those records across time against later alteration is Immutability. (3) Non-Repudiation — attributability of writes: durable, attributable logging of which agent/generation performed which mutation (provenance of the self-modification chain as evidence). I require provenance stamps as a write-path validation input, but the durability/attributability of the audit record itself is Non-Repudiation. (4) Confidentiality — the exfiltration/read face of prompt injection, retrieval of sensitive context from a poisoned RAG store, model/prompt extraction, and leakage of provider API keys; I only own the WRITE-INTO-store side of memory/RAG poisoning. (5) Availability/Unbounded Consumption (LLM10) — runaway self-improvement loops, retry storms, and resource exhaustion route to Availability; I touch idempotency only as a write-correctness (no-duplicate-mutation) contract, not as a rate/quota control. (6) Resilient — sandbox/isolation as a containment-and-recovery posture is Resilient's; I cite the sandbox only as the enforcement point for a write-authorization contract.

## Availability  (common-patterns/availability.md)

### Unbounded autonomous-loop consumption (no generation, token, wall-clock, or cost budget)

- **Threat:** An autonomous task loop or self-improvement loop with no hard upper bound on iterations, tokens, tool calls, or spend runs until it exhausts a provider quota, a wallet, or a compute budget — converting normal operation (or a single adversarial task) into an availability-and-cost denial-of-service. This is the availability face of Excessive Agency: the agent has the agency to consume without a ceiling that fails closed.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency  |  ATLAS LLM Denial of Service (cost/resource exhaustion); Cost Harvesting  |  MAESTRO L1 Foundation Models (token/inference cost); L3 Agent Frameworks (loop control); L4 Deployment & Infrastructure (compute/quota)
- **SIA:** SIA's Feedback Agent rewrites target_agent.py across N generations bounded only by --max_gen; if --max_gen is unset, mis-set high, or the per-generation token/wall-clock cost is not separately capped, a run can burn the entire budget on multiple model-provider keys before the benchmark loop terminates. Each generation also re-runs the Target Agent (which executes arbitrary Python) against the benchmark, multiplying per-generation cost. Availability pattern requires: a hard --max_gen ceiling that fails closed, plus an orthogonal aggregate token/spend/wall-clock budget enforced across generations and across all provider keys, not just an iteration count.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06]  mitre_attack=[T1499.003, T1496]  cwe=[CWE-770, CWE-400, CWE-834]
- **nist_families:** SC, SI, CP, RA

### Model-provider dependency reliability — no SLA, rate-limit headroom, or degraded-mode plan

- **Threat:** The agent's critical path depends synchronously on one or more external model-provider APIs (and tool/RAG/vector-store backends) whose availability, rate limits, and latency the agent does not control. Provider 429/5xx throttling, a regional provider outage, or a latency spike stalls or fails autonomous task completion. Without a documented provider SLA, rate-limit headroom posture, and a failover/degraded-mode plan, agent availability is silently inherited from the least-available dependency.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM03 Supply Chain  |  ATLAS LLM Denial of Service; ML Supply Chain Compromise (availability dimension of provider dependency)  |  MAESTRO L1 Foundation Models; L4 Deployment & Infrastructure; L7 Agent Ecosystem (external service dependencies)
- **SIA:** SIA calls multiple model-provider APIs through the Claude Agent SDK + OpenHands for the Meta-Agent, Target Agent, and Feedback Agent. A provider rate-limit (429) or outage mid-run stalls the generation loop and can corrupt the runs/run_id/gen_n/ artifact sequence. Availability pattern requires: documented per-provider availability target, latency budget (p50/p95/p99), and rate-limit ceiling; headroom of provisioned RPM/TPM versus the loop's per-generation demand; and a degraded-mode plan (provider failover, generation checkpoint/resume, fail-the-run-cleanly) rather than an indefinite stall.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM03]  mitre_attack=[T1499]  cwe=[CWE-1059, CWE-703]
- **nist_families:** CP, SC, SI, SR, RA

### No SLO/SLI for autonomous task completion (success ratio, time-to-completion, decision-timeliness)

- **Threat:** The system makes autonomous, consequential decisions (tool invocations, code execution, multi-step task completion) with no declared service-level objective for task-completion success ratio, end-to-end completion latency, or decision-timeliness, and no error budget. Without SLOs you cannot verify the agent meets implicit availability/timeliness commitments, cannot detect silent degradation (e.g., a model or prompt change that drops the success ratio), and cannot prioritize reliability work. Decision-timing constraints (a task whose value expires if not completed within a window) are unenforced.
- **Grounding:** OWASP LLM09 Misinformation (degraded-success masquerading as completion); LLM06 Excessive Agency (acting past a timeliness boundary)  |  ATLAS ML Model Performance Degradation / drift (observability dimension)  |  MAESTRO L5 Evaluation & Observability; L3 Agent Frameworks; L6 Security & Compliance (cross-cutting)
- **SIA:** SIA optimizes a scalar metric against a benchmark, but the framework itself lacks an SLO for the optimization run: there is no declared target for run success ratio, no per-generation completion-latency SLI, and no error budget that distinguishes a clean failed generation from a stalled/hung one. Availability pattern requires: an SLO for run completion (e.g., fraction of generations that produce a valid agent_execution.json within a wall-clock budget), an SLI for time-to-completion per generation, and burn-rate alerting so a regression that stalls or silently degrades the loop is caught rather than discovered at budget exhaustion.
- **taxonomy_mappings:** owasp_llm_top10=[LLM09, LLM06]  mitre_attack=[]  cwe=[CWE-1119, CWE-703]
- **nist_families:** CP, SI, AU, RA

### Capacity headroom for concurrent agents and execution sandboxes (no ceiling on parallel agents/runs)

- **Threat:** Multi-agent systems and parallel autonomous runs spawn agents, sub-agents, and code-execution sandboxes without a provisioned-capacity ceiling or headroom posture. Concurrent agents contend for the same finite resources — provider rate-limit quota (shared TPM/RPM), sandbox compute, the orchestrator/event-bus, and shared state stores — so that fan-out (or an agent that spawns sub-agents) exhausts capacity for all tenants on the shared substrate. This is the agentic analogue of application-exhaustion: legitimate-shape agent traffic saturates the substrate.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency  |  ATLAS LLM Denial of Service (resource exhaustion); Cost Harvesting  |  MAESTRO L4 Deployment & Infrastructure; L3 Agent Frameworks (orchestration/fan-out); L7 Agent Ecosystem (multi-agent contention)
- **SIA:** SIA writes artifacts under runs/run_id/gen_n/ and executes the generated target_agent.py (arbitrary Python) once per generation; running multiple concurrent runs, or a target that itself fans out work, contends for the same provider quota and the same host compute/disk without a declared concurrent-run ceiling. Availability pattern requires: a hard cap on concurrent agents/runs/sandboxes, a headroom ratio of provisioned capacity (compute, provider TPM/RPM, disk for run artifacts) to observed peak fan-out, and a load-test artifact showing graceful shed-load rather than substrate exhaustion when concurrency is maxed.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06]  mitre_attack=[T1499.003, T1496]  cwe=[CWE-770, CWE-400, CWE-410]
- **nist_families:** SC, CP, SI, RA

### Failure-domain & blast-radius analysis for shared agent substrate (orchestrator, state store, provider key, held-out ground truth)

- **Threat:** Agentic systems concentrate fate-sharing in a few single points: a single orchestrator/scheduler, a shared message bus or memory/state store, a single model-provider key or account, and (for evaluation systems) a single held-out ground-truth/benchmark store. The failure-domain map showing which agents share which fate is undocumented, so an outage of one shared component silently fails the entire fleet, and no DR/BCP RTO/RPO is stated per critical data class (run artifacts, evaluation ground truth, agent memory).
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM03 Supply Chain  |  ATLAS ML Model Performance Degradation (loss-of-evaluation availability)  |  MAESTRO L4 Deployment & Infrastructure; L2 Data Operations (ground-truth/artifact stores); L7 Agent Ecosystem (shared-fate across agents)
- **SIA:** SIA's held-out private ground truth (data/private/, evaluate.py) is the single component whose loss or corruption invalidates every generation's score and halts the optimization loop — it is the fitness-function's availability single point of failure. runs/run_id/gen_n/ artifacts and the orchestrating loop are likewise unreplicated by default. Availability pattern requires: a failure-domain diagram naming what shares fate (orchestrator, provider key/account, the data/private/ store, agent_execution.json artifact path); a blast-radius statement per shared component; and DR RTO/RPO per data class — held-out ground truth and prior-generation artifacts in particular — with a tested restore.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM03]  mitre_attack=[T1485]  cwe=[CWE-1188, CWE-400]
- **nist_families:** CP, SC, SR, RA, SI

### Shallow agent health checks & no liveness/progress detection for stuck loops

- **Threat:** Agent health is monitored as a process-up / port-open / HTTP-200 liveness check that cannot distinguish a healthy agent from one that is hung mid-tool-call, stuck in a non-progressing reasoning loop, repeatedly retrying a throttled provider, or producing degraded output. Shallow checks let an orchestrator keep routing tasks to (or keep budget-burning on) an agent that is alive but making no forward progress, masking degradation until a deadline or budget is blown.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM09 Misinformation (silent quality degradation)  |  ATLAS ML Model Performance Degradation  |  MAESTRO L5 Evaluation & Observability; L3 Agent Frameworks; L6 Security & Compliance (cross-cutting)
- **SIA:** SIA has no deep liveness/progress signal between generations: a Target Agent that hangs on an external call or loops without advancing the scalar metric is indistinguishable, to a shallow check, from one making progress — it simply consumes the per-generation budget. Availability pattern requires: a progress/liveness SLI (e.g., per-generation watchdog timeout, metric-improvement-or-abort, agent_execution.json freshness check) that detects a non-progressing generation and fails it closed rather than letting it run to budget exhaustion.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM09]  mitre_attack=[]  cwe=[CWE-835, CWE-1119, CWE-703]
- **nist_families:** SI, CP, AU

**Multi-agent / self-improvement coverage:** MULTI-AGENT: Two patterns are explicitly multi-agent on the Availability axis. "Capacity headroom for concurrent agents and execution sandboxes" addresses fan-out contention — multiple agents/sub-agents sharing finite provider quota (TPM/RPM), sandbox compute, and the orchestrator/bus, where one agent's spawn behavior or a fleet's concurrency exhausts the shared substrate for all (MAESTRO L7 multi-agent contention, L4 infra). "Failure-domain & blast-radius analysis for shared agent substrate" covers the shared-fate single points multi-agent systems concentrate — one orchestrator, one state/memory bus, one provider key/account — whose outage silently fails the whole fleet, and demands a fate-sharing map plus per-data-class DR RTO/RPO. Multi-agent integrity/identity threats (collusion, Sybil, impersonation, inter-agent message interception, goal-manipulation cascades) are deliberately NOT designed here — they are not Availability concerns; see lens_boundaries. SELF-IMPROVEMENT (SIA-class): fully covered and instantiated. "Unbounded autonomous-loop consumption" is the canonical runaway self-improvement loop — it requires a hard --max_gen ceiling that fails closed PLUS an orthogonal aggregate token/wall-clock/spend budget across all generations and all provider keys (an iteration count alone is insufficient). "No SLO/SLI for autonomous task completion" gives the self-improvement loop a run-completion success-ratio SLO, a per-generation completion-latency SLI, and burn-rate alerting so a regression that stalls or silently degrades the loop is caught. "Shallow agent health checks / progress detection" adds the per-generation watchdog and metric-improvement-or-abort progress signal that distinguishes a progressing generation from a hung one. "Failure-domain analysis" names SIA's held-out private ground truth (data/private/, evaluate.py) as the fitness-function availability single point of failure and asks for DR RTO/RPO on the ground-truth and prior-generation artifact stores.

**Lens boundaries:** Routed OUT of Availability (named, not designed here): (1) BEHAVIOR UNDER FAILURE / retry semantics — circuit breakers, bulkheads, backpressure, retry-with-jitter, thundering-herd avoidance, and graceful-degradation logic when a provider throttles or a tool fails → ROUTE to Resilient (common-patterns/resilient.md). Availability owns SLO/SLI, headroom, health checks, dependency SLAs, and the DR/BCP envelope; Resilient owns how the system behaves once a failure-domain is hit. (2) TOPOLOGY / REPLICATION — multi-region placement, replica/quorum design, orchestrator and state-store replication, agent-fleet placement → ROUTE to Distributed (common-patterns/distributed.md). My patterns surface the need ('this shared component is a single point of fate', 'this provider needs failover headroom') but the topology change that fixes it is owned by Distributed. (3) CREDENTIAL LIFETIME — rotation/TTL of the multiple model-provider API keys and agent credentials → ROUTE to Ephemeral (common-patterns/ephemeral.md); Availability only treats the provider key as a capacity/fate dependency, not its lifecycle. (4) MULTI-AGENT IDENTITY/INTEGRITY threats — Sybil identities, agent impersonation, inter-agent message interception, collusion, goal-manipulation cascades → ROUTE across Authenticity (impersonation/Sybil identity), Confidentiality/Integrity (inter-agent message interception/tampering), and Integrity (collusion, goal-manipulation cascades). (5) PROMPT-INJECTION-DRIVEN resource exhaustion as a manipulation vector (LLM01 root cause) → the injection-handling control is Integrity's; Availability owns only the consumption-ceiling that bounds the blast radius regardless of trigger. (6) POISONING of the held-out ground truth as a correctness/trust attack → ROUTE to Integrity (Data & Model Poisoning, LLM04); Availability owns only that ground-truth's loss-of-availability single-point-of-failure and its DR posture.

## Distributed  (common-patterns/distributed.md)

### Orchestrator / control-plane as single point of failure

- **Threat:** The agent orchestrator (task router, generation scheduler, tool-dispatch broker, or the loop driver that sequences plan->act->observe steps) is the single coordination authority for the whole agent system. If it is single-instance, single-AZ, or holds the only copy of the run's coordination state, a zonal or process failure halts every in-flight agent and every multi-agent workflow at once. The topology question is whether the control plane is replicated across failure domains and whether its coordination state is externalized so a replacement instance can resume; behavior-under-failure and uptime targets are routed out of lens.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM10 Unbounded Consumption  |  ATLAS LLM Plugin Compromise (orchestration/tool-dispatch surface, as prose context)  |  MAESTRO L3 Agent Frameworks; L4 Deployment & Infrastructure; L7 Agent Ecosystem
- **SIA:** SIA's generation loop (the Feedback Agent driving Meta-Agent -> Target Agent -> evaluate across --max_gen generations) is a single sequential control plane. The run's coordination state lives in runs/run_id/ (per-generation artifacts, agent_execution.json, the current best metric/lineage). It is single-process and single-host by construction; if that process or its host fails mid-run, the multi-generation lineage cannot resume because the next-generation selection state is not externalized to a redundant store. Note: SIA is a single-node research harness, so this is a topology observation about its control plane, not a production HA claim.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM10]  mitre_attack=[]  cwe=[CWE-1188, CWE-710]
- **nist_families:** SC, CP, CM, RA

### Model-provider / inference endpoint as single point of failure

- **Threat:** Every agent step depends on a model-inference call. When the system is pinned to one provider, one region of that provider, one API key, or one model family, that dependency is the failure domain for the entire agent population: a provider/region outage or a single-key throttle stalls all agents simultaneously. The distributed-lens questions are provider/endpoint topology (single vs multi-provider/multi-region), whether inference routing distributes across endpoints, and whether the key/quota surface is partitioned so one limit does not stop all agents. Failover behavior and SLO targets are routed out of lens.
- **Grounding:** OWASP LLM03 Supply Chain; LLM10 Unbounded Consumption  |  ATLAS ML Supply Chain Compromise (model-provider dependency, as prose context)  |  MAESTRO L1 Foundation Models; L4 Deployment & Infrastructure
- **SIA:** SIA calls multiple model-provider APIs and is built on the Claude Agent SDK + OpenHands; the Meta-Agent, Target Agent, and Feedback Agent all depend on live inference. If all three roles route to the same provider/region (or share a single key per provider), that provider is a SPOF for the whole self-improvement run, and a single provider-side rate-limit or regional outage stalls every generation. The multi-provider-key setup is a partial mitigation only if the roles are actually distributed across providers rather than all defaulting to one.
- **taxonomy_mappings:** owasp_llm_top10=[LLM03, LLM10]  mitre_attack=[]  cwe=[CWE-1188, CWE-1357]
- **nist_families:** SC, CP, SR, RA

### Stateful agent memory vs stateless workers boundary

- **Threat:** Long-running agents accumulate task state in-process: conversation/scratchpad memory, partial plans, tool-call context, accumulated retrieval results. When this state lives only in worker memory, the worker is stateful and cannot be load-balanced, horizontally scaled, or rescheduled without losing the agent's working context — and any sticky routing to a specific worker recreates a per-agent SPOF. The lens question is where the stateful/stateless boundary sits: is agent working state externalized to a redundant store so workers are interchangeable, or is it pinned in a pod that takes the task down with it on restart/eviction/AZ loss.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM08 Vector & Embedding Weaknesses  |  ATLAS n/a (topology/state-boundary concern, no clean ATLAS technique)  |  MAESTRO L3 Agent Frameworks; L4 Deployment & Infrastructure
- **SIA:** SIA's Target Agent state (the generated target_agent.py, its in-run execution context, agent_execution.json log) is materialized to the local run directory rather than held purely in memory, which is good for resumability of a single generation; but the orchestration's in-flight selection/lineage state across generations is in-process. The stateful boundary is the per-generation artifact directory — interchangeable workers would require that the active-generation working state, not just the completed-generation log, be externalized.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06]  mitre_attack=[]  cwe=[CWE-1188, CWE-710]
- **nist_families:** SC, CP, CM

### Multi-agent topology, message routing, and CAP positioning under partition

- **Threat:** In multi-agent systems, agents coordinate through an inter-agent message fabric (a broker, a blackboard, a shared task queue, or direct peer routing). The distributed-lens concerns are the routing topology (star through a coordinator vs mesh vs queue), whether a network partition splits the agent set, and the CAP position chosen when it does: does the system prefer consistency (pause agents on the minority partition so they cannot act on stale shared goal/state) or availability (let partitioned agents keep acting on a possibly-stale shared objective). An unspecified partition policy means partitioned sub-agents can pursue a stale or diverged goal — a goal-manipulation/divergence cascade rooted in topology, not in adversarial input. Whether the partition is reached adversarially (impersonation, Sybil routing) is grounded as prose; the topology/consistency choice is the in-lens artifact.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM09 Misinformation  |  ATLAS LLM Prompt Injection (cross-agent goal-manipulation vector, as prose context); MAESTRO multi-agent collusion / agent impersonation / inter-agent communication interception are the prose anchors  |  MAESTRO L7 Agent Ecosystem; L3 Agent Frameworks; L2 Data Operations
- **SIA:** n/a — SIA is a sequential single-node pipeline (Meta -> Target -> Feedback), not a concurrent multi-agent mesh, so there is no inter-agent message fabric to partition. The pattern is carried for the broad multi-agent surface the pack must serve; SIA exercises only the sequential-handoff variant, where the analog risk is a stale lineage/best-metric handoff between generations rather than a partition split.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM09]  mitre_attack=[]  cwe=[CWE-362, CWE-1188]
- **nist_families:** SC, CP, AC, SI

### Shared vector store / agent memory — locality, replication, and cross-region consistency

- **Threat:** A shared vector store or long-term agent memory is a stateful backing service that many agents read and write concurrently. The distributed-lens questions are: is it a single instance (SPOF for every agent that depends on retrieval), what is its replication topology and data locality (does tenant/run memory replicate cross-region, and is residency bound per tenant), and what is the cross-region consistency model for writes — because asynchronous replication means an agent in region B can retrieve stale or not-yet-replicated memory written in region A, producing divergent agent behavior from a consistency gap rather than from poisoned content. Detecting poisoned/adversarial embeddings is out of lens (routed to Integrity); the in-lens artifact is the store's SPOF status, replication topology, locality, and write-consistency model.
- **Grounding:** OWASP LLM08 Vector & Embedding Weaknesses; LLM02 Sensitive Information Disclosure  |  ATLAS n/a for the topology concern (ATLAS 'LLM Data Leakage'/'Erode ML Model Integrity' touch the content side, which is routed out of lens)  |  MAESTRO L2 Data Operations; L4 Deployment & Infrastructure
- **SIA:** SIA's persistent state is the benchmark with HELD-OUT private ground truth (data/private/, evaluate.py) plus the runs/run_id/gen_n/ artifact tree, rather than a vector store. In lens, this is a data-locality and replication-topology observation: the private ground truth is a single-locality store whose integrity and locality gate every generation's score; if it were replicated for HA, the cross-region consistency of that ground truth would itself become an attack/inconsistency surface. Confidentiality of the held-out set (leakage into a replica an agent can read) is routed to Confidentiality.
- **taxonomy_mappings:** owasp_llm_top10=[LLM08, LLM02]  mitre_attack=[T1565]  cwe=[CWE-1188, CWE-362]
- **nist_families:** SC, CP, SI, AC

### Sub-agent fan-out and inference load distribution

- **Threat:** Autonomous loops and planner/worker patterns fan out sub-agents (parallel tool calls, spawned worker agents, recursive sub-task delegation). Without bounded fan-out and load distribution across inference endpoints and worker pools, fan-out concentrates load on one endpoint/key/worker tier and self-amplifies — a self-inflicted hot spot that becomes a distributed-availability failure for the whole agent population, and a single throttled endpoint then stalls the fan-out. The in-lens artifact is the load-distribution topology and concurrency/fan-out bounds across endpoints and worker pools; the per-task spend ceiling and runaway-loop kill switch are the Resilient/Availability concern and routed there.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency  |  ATLAS LLM Denial of Service (resource-amplification framing, as prose context)  |  MAESTRO L4 Deployment & Infrastructure; L3 Agent Frameworks; L5 Evaluation & Observability
- **SIA:** SIA's fan-out is bounded structurally by --max_gen (generation depth) rather than concurrent breadth, and each generation's target_agent.py EXECUTES arbitrary Python, so an emergent generated target could itself spawn unbounded parallel work or recursive inference calls that concentrate on the shared provider/key. The distributed concern is that all generations route through the same inference endpoints/keys, so generated-code fan-out has no load-distribution headroom and concentrates on a single endpoint tier.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06]  mitre_attack=[T1499]  cwe=[CWE-770, CWE-400]
- **nist_families:** SC, CP, RA

**Multi-agent / self-improvement coverage:** MULTI-AGENT surface is covered primarily by three patterns. The "Multi-agent topology, message routing, and CAP positioning under partition" pattern is the core multi-agent artifact: it makes the inter-agent message fabric, routing topology (star/mesh/queue), partition behavior, and the explicit consistency-vs-availability choice the thing the analyst must extract — and it names the MAESTRO multi-agent threats (collusion, agent impersonation, inter-agent comms interception, goal-manipulation cascade) as prose anchors while keeping only the topology/consistency choice in lens. "Orchestrator/control-plane as SPOF" covers the star-topology coordinator that most multi-agent systems route through (the single coordination authority). "Sub-agent fan-out and inference load distribution" covers planner/worker and recursive-delegation multi-agent shapes from the load-distribution angle. "Shared vector store / agent memory locality" covers the shared-blackboard/shared-memory coordination substrate that multiple agents read-write concurrently, with cross-region write-consistency as the divergence vector. SELF-IMPROVEMENT (SIA-class) is covered end-to-end through the per-pattern SIA instantiations: the generation loop is profiled as a single sequential control plane (Pattern 1), the multi-provider-key inference dependency is profiled as a provider SPOF across the Meta/Target/Feedback roles (Pattern 2), the per-generation artifact tree is profiled as the stateful/stateless boundary and resumability question (Pattern 3), the held-out private ground truth (data/private/, evaluate.py) is profiled as a single-locality replication/consistency surface (Pattern 5), and the arbitrary-Python-executing generated target plus --max_gen depth is profiled as the self-amplifying fan-out concern (Pattern 6). Pattern 4 honestly marks SIA n/a (sequential pipeline, no mesh to partition) while still carrying the multi-agent variant for the broad surface, and reframes the SIA analog as stale lineage/best-metric handoff between generations.

**Lens boundaries:** Routed OUT to adjacent goals: (1) Uptime/SLO targets, RTO/RPO numbers, and availability percentages -> Availability — Distributed owns whether the topology has redundant failure domains, not the numeric target. (2) Behavior-under-failure: failover orchestration, graceful degradation, circuit-breaking, runaway-loop kill switches, per-task spend ceilings, and recovery sequencing -> Resilient — Distributed states the partition/CAP position and the load-distribution topology, but the system's reaction to a failure is Resilient's. (3) Detecting poisoned embeddings, adversarial/poisoned shared-memory content, and integrity of replicated state content -> Integrity — Pattern 5 keeps only the store's SPOF/replication/consistency topology in lens and routes content trust out. (4) Confidentiality of the held-out private ground truth and leakage of memory/secrets into a replica an agent can read -> Confidentiality — Pattern 5 flags the locality/replication surface but routes the leakage consequence out. (5) Authenticity of inter-agent identity, agent impersonation, and Sybil-identity admission control -> Authenticity/Identity — Pattern 4 names impersonation/Sybil as the adversarial route to a partition split (prose grounding) but keeps only the topology/consistency choice in lens; how an agent's identity is issued and verified is Authenticity's. (6) Tamper-evidence and replication continuity of the agent-action audit/log store (agent_execution.json) -> Non-Repudiation/Immutability — Distributed would only flag cross-region audit-replication lag as a topology fact and cross-reference, not own the tamper-evidence guarantee.

## Resilient  (common-patterns/resilient.md)

### No circuit breaker on the autonomous self-improvement / task loop (runaway generations)

- **Threat:** An autonomous agent loop with no trip condition keeps iterating on a degrading or adversarially-steered objective: hallucinated 'progress', reward-hacked metric gains, or an injected goal that never converges. Without a breaker the loop burns budget, mutates artifacts, and amplifies a single bad generation across all subsequent ones. This is the Resilient (loop-termination) facet of Excessive Agency, distinct from the per-step authorization facet that Confinement owns.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM10 Unbounded Consumption; LLM09 Misinformation  |  ATLAS LLM Prompt Injection (AML.T0051) as a loop-steering vector; LLM Jailbreak as a guardrail-bypass that keeps the loop running; broadly relates to autonomous-agent abuse / 'cost harvesting' style consumption abuse  |  MAESTRO L3 Agent Frameworks (the orchestration loop itself); L5 Evaluation & Observability (the metric/feedback signal that should arm the breaker); L1 Foundation Models (hallucinated convergence)
- **SIA:** SIA's Feedback Agent rewrites target_agent.py across --max_gen generations optimizing a scalar metric. The breaker must trip on signals beyond just hitting max_gen: N consecutive generations with no metric improvement (or metric improving only on the public set while held-out data/private/ ground truth via evaluate.py stagnates or regresses = overfitting/reward-hacking signal), repeated identical-diff rewrites (loop stuck), or a generation whose execution error-rate spikes. Trip = halt the run_id, freeze runs/run_id/gen_n/ artifacts, page a human; do not silently roll to gen_n+1.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM10, LLM09]  mitre_attack=[T1496]  cwe=[CWE-835, CWE-691, CWE-1284]
- **nist_families:** SI, SC, CP, RA, AU

### Retry/backoff discipline on model + tool calls (jitter, per-dependency budget, idempotency interaction)

- **Threat:** Agents make many model-provider and tool calls per step; naive retry on 429/5xx/timeout without exponential backoff + jitter + a bounded per-dependency budget produces synchronized retry storms against the provider (self-inflicted rate-limit lockout, runaway spend) and duplicate side effects when a tool call is non-idempotent (double file write, double external POST, double sub-agent spawn). The Resilient concern is the retry policy's shape and budget; the spend cap itself is Unbounded-Consumption shared with Confinement.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM05 Improper Output Handling (re-issuing a side-effecting tool call on retry)  |  ATLAS relates to LLM Denial of Service / resource-exhaustion patterns and cost-harvesting style consumption abuse against the model endpoint  |  MAESTRO L3 Agent Frameworks (retry middleware around tool/model clients); L1 Foundation Models (provider rate-limit / availability behavior); L4 Deployment & Infrastructure (provider quota exhaustion)
- **SIA:** SIA calls multiple model-provider APIs (multiple keys) and the target executes arbitrary Python that may itself hit tools/network. A failing provider with fixed-interval retry across the Meta/Target/Feedback agents produces a synchronized storm that exhausts every key's quota at once (correlated failure of the supposed redundancy). Each generation should carry a retry budget; a retried target-execution step must be idempotent or guarded so a re-run does not double-append to agent_execution.json or double-spend on a downstream tool.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM05]  mitre_attack=[T1496]  cwe=[CWE-799, CWE-770, CWE-1284]
- **nist_families:** SI, SC, CP

### Bulkheads / resource isolation around code-exec sandboxes and per-agent quotas

- **Threat:** Agentic systems run generated/arbitrary code and fan out to sub-agents that share an execution substrate (thread pool, container host, disk, file descriptors, API-key pool, message bus). Without bulkheads, one runaway or hostile unit — a fork-bombing generated script, a sub-agent stuck in a tool loop, a single tenant's task — starves every other concurrent agent/run. The Resilient concern is fault-domain isolation (blast-radius containment of a failure); the security-boundary/escape concern of the sandbox itself is Confinement's.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency; LLM05 Improper Output Handling (executing generated output)  |  ATLAS relates to compromised/abused agent code-execution and resource hijacking via generated code; LLM Prompt Injection as the trigger that makes a sub-agent go rogue  |  MAESTRO L4 Deployment & Infrastructure (sandbox/container isolation, cgroups/ulimits); L3 Agent Frameworks (per-agent resource accounting); L7 Agent Ecosystem (cross-agent resource contention in multi-agent deployments)
- **SIA:** SIA's Target Agent executes arbitrary Python the Meta-Agent generated. A bulkhead must cap each generation's execution in its own resource-limited sandbox (CPU/mem/wallclock/disk/network ulimits, no access to sibling runs/run_id/ trees or to data/private/) so a runaway or hostile generated script cannot starve concurrent run_ids, exhaust the host, or reach into another generation's artifacts. Each run_id should also draw from an isolated slice of the API-key pool so one run cannot drain the keys others depend on.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06, LLM05]  mitre_attack=[T1496, T1499]  cwe=[CWE-770, CWE-400, CWE-693]
- **nist_families:** SC, SI, CM, AC

### Timeout discipline on autonomous steps, tool calls, and reasoning chains (hang / infinite-loop containment)

- **Threat:** Every autonomous step is a potential hang: a tool call that never returns, a model request that stalls, a generated subprocess that blocks on stdin/network, or a reasoning chain that loops without making progress. Absent a wall-clock timeout on each step AND a total budget on the chain, a single hung step pins a worker indefinitely and the agent silently stops making progress with no failure signal. Timeout discipline is the per-step/per-chain deadline; loop-termination logic that decides what to do at the deadline overlaps the circuit-breaker pattern above.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency  |  ATLAS relates to LLM Denial of Service via long-running / non-terminating generation and tool invocation  |  MAESTRO L3 Agent Frameworks (per-step deadline enforcement); L1 Foundation Models (streaming/generation stall); L4 Deployment & Infrastructure (subprocess wall-clock kill)
- **SIA:** SIA's generated target_agent.py runs an arbitrary task; without a hard wall-clock timeout the execution step can hang (blocking I/O, infinite loop in generated code, a stalled provider call) and pin the generation forever, stalling the run with no entry written to agent_execution.json. Each generation needs a per-execution timeout that kills the subprocess, a separate timeout on each Meta/Feedback model call, and a total per-generation deadline so a hung step deterministically fails the generation instead of hanging the whole run_id.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06]  mitre_attack=[T1499]  cwe=[CWE-835, CWE-1088, CWE-400]
- **nist_families:** SI, SC, CP

### Graceful degradation when a model, tool, or guardrail is down (fail-safe, not fail-open-and-keep-acting)

- **Threat:** When a dependency degrades, an autonomous agent must NOT proceed as if it were healthy. Two failure shapes matter: (1) a model/tool outage where the agent should fall back (cheaper/secondary model, cached result, queued retry, or explicit halt with status) rather than emit a confident hallucination or proxy a raw error into a downstream action; (2) guardrail-failure-open, where the safety filter / output validator / policy check errors out and the agent treats 'check unavailable' as 'check passed' and keeps taking consequential actions. The Resilient concern is the degradation mode's correctness; the topology/replication of the dependency is Distributed's, the uptime SLO is Availability's.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM09 Misinformation; LLM05 Improper Output Handling; LLM01 Prompt Injection (a down guardrail removes the injection defense)  |  ATLAS LLM Jailbreak / guardrail bypass that is functionally equivalent to a guardrail failing open; relates to LLM Prompt Injection succeeding once the validating filter is unavailable  |  MAESTRO L6 Security & Compliance (cross-cutting guardrail availability); L1 Foundation Models (model fallback); L3 Agent Frameworks (degraded-mode orchestration); L5 Evaluation & Observability (detecting the degraded state)
- **SIA:** If SIA's primary provider is down, the loop must degrade deterministically (secondary key/model, or halt the run with a recorded reason) rather than silently produce low-quality rewrites that still get scored and promoted. Critically, if the scoring/guardrail path degrades — evaluate.py errors, the held-out data/private/ ground truth is unreachable, or an output-safety check on generated code fails open — the framework must NOT treat a missing/failed evaluation as a passing or default-high score and promote that generation; it must fail the generation safe and stop, not fail open and keep self-modifying.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM09, LLM05, LLM01]  mitre_attack=[]  cwe=[CWE-636, CWE-755, CWE-754, CWE-391]
- **nist_families:** CP, SI, SC, RA

### Backpressure on generation / sub-agent fan-out and on the inter-agent message bus

- **Threat:** Multi-agent systems and self-improvement loops fan out work faster than downstream stages can absorb it: a planner spawns sub-agents unboundedly, a generation enqueues more candidate rewrites than the evaluator can score, or agents flood a shared message bus. Without bounded queues, admission control, and shed-load, the system accumulates unbounded in-flight work — memory blowup, queue collapse, or a goal-manipulation/feedback cascade where one agent's bad output is consumed and re-amplified by many others before any backpressure stops it. Backpressure is the flow-control concern; the breaker decides when to stop generations, backpressure decides how many may be in flight at once.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency; LLM09 Misinformation (cascade amplification)  |  ATLAS relates to multi-agent abuse / agent-impersonation flooding and LLM Denial of Service via unbounded fan-out; consumption/cost-harvesting style abuse of the shared substrate  |  MAESTRO L7 Agent Ecosystem (inter-agent communication, collusion/Sybil flooding, impersonation on the bus); L3 Agent Frameworks (bounded work queues, admission control); L2 Data Operations (unbounded artifact/log accumulation)
- **SIA:** SIA is single-lineage per run_id but fan-out backpressure still bites if multiple run_ids or multiple candidate rewrites per generation outrun evaluate.py: candidate scoring should be a bounded queue with shed-load, and runs/run_id/gen_n/ artifact + agent_execution.json growth should be bounded so an unbounded-generation run cannot fill disk. In a genuinely multi-agent variant, bound the per-planner sub-agent spawn count and rate-limit the inter-agent channel so one impersonating or runaway agent cannot flood peers and drive a goal-manipulation cascade.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06, LLM09]  mitre_attack=[T1499, T1496]  cwe=[CWE-770, CWE-400, CWE-410]
- **nist_families:** SC, SI, AU, CP

**Multi-agent / self-improvement coverage:** SELF-IMPROVEMENT (SIA-class) is covered as a first-class failure surface across the catalog rather than bolted on: Pattern 1 (circuit breaker) is the load-bearing self-improvement control — it arms on metric stagnation, public-vs-held-out divergence (the reward-hacking/overfitting tell against data/private/ + evaluate.py), and identical-diff loops, then halts the run and freezes artifacts instead of rolling to the next generation. Pattern 4 (timeouts) contains the arbitrary-code-execution hang per generation; Pattern 5 (graceful degradation) carries the safety-critical fail-safe rule for the self-improvement loop specifically — a degraded/unreachable evaluator or output-safety check must NOT score-as-pass and promote a self-modification, it must fail safe and stop. Pattern 2 (retry budgets) and Pattern 3 (sandbox bulkheads, per-run key-pool slices, no cross-run artifact reach) contain the blast radius of each generation's execution. MULTI-AGENT surface: Pattern 3 isolates concurrent agents/runs into separate fault domains so one rogue or starved unit cannot starve peers; Pattern 6 directly addresses inter-agent flow control — bounded sub-agent spawn, rate-limited inter-agent channel, and shed-load to stop a goal-manipulation/feedback cascade (MAESTRO L7) where one agent's bad or impersonated output is consumed and re-amplified by many. Pattern 2's correlated-failure note (synchronized retry storm draining a shared key pool) is itself a multi-agent resilience failure. Together the six cover the broad agentic surface (single tool-use agent, multi-agent fan-out, autonomous loop) and fully cover the self-improvement sub-surface.

**Lens boundaries:** Routed OUT of Resilient by design: (1) The per-step authorization / least-privilege / sandbox-escape security boundary of the code-exec environment goes to CONFINEMENT (Excessive Agency's authz facet, LLM06); here I only own the sandbox as a fault-isolation bulkhead, not as a trust boundary. (2) The absolute spend/token/quota CAP as a cost-control policy (Unbounded Consumption as budget governance) is shared with Confinement; I own only the shape of retry/backoff and backpressure flow-control, not the cap value or who sets it. (3) Dependency REPLICATION and multi-region/topology of models, tools, queues, and the message bus go to DISTRIBUTED (NOT my lens per the brief); I own the degradation MODE, not the topology that provides the redundancy. (4) UPTIME TARGETS / SLOs / error-budget math for the agent service and its dependencies go to AVAILABILITY (NOT my lens per the brief); my graceful-degradation and circuit-breaker patterns frequently MERGE with an Availability finding — flag via related_concerns rather than duplicating. (5) Integrity/idempotency of tool side-effects and of the agent_execution.json / artifact writes is INTEGRITY's; I reference idempotency only where it changes whether a retry is safe. (6) Auditability of breaker-trip and degraded-mode events (who was paged, immutable trip record) is NON-REPUDIATION / AUDITABILITY-tier; I note the trip must be observable but route the audit-pipeline durability there. (7) Prompt-injection DETECTION/PREVENTION as a content control is Confinement/Confidentiality's; I reference injection only as the upstream trigger that arms a breaker or makes a guardrail's fail-open mode dangerous.

## Ephemeral  (domains/agentic-ai/common-patterns/ephemeral.md)

### Standing broad agency vs. JIT scoped tool credentials

- **Threat:** An agent (or any sub-agent it spawns) holds long-lived, broadly-scoped tool/provider credentials that grant far more capability than any single task needs. A prompt-injected or jailbroken agent then wields the full standing permission set; excessive agency is amplified because the credential is permanent, not just the over-broad grant. The fix in this lens is lifecycle: mint per-task, narrowly-scoped, short-TTL tool credentials just-in-time and let them expire, so a hijacked turn cannot reach beyond the task's grant or outlive it.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM01 Prompt Injection  |  ATLAS LLM Prompt Injection (AML.T0051); LLM Jailbreak (AML.T0054)  |  MAESTRO L3 Agent Frameworks; L4 Deployment & Infrastructure; L7 Agent Ecosystem
- **SIA:** SIA's Target Agent runs against tasks while the Meta/Feedback agents drive the loop; all stages share the same multi-provider model API keys with no per-generation scoping or TTL. A standing broad key means any one generation's code-exec (target_agent.py runs arbitrary Python) inherits full standing agency to every provider and tool the key reaches. Ephemeral fix: issue per-run_id/gen_n scoped tokens that expire when the generation completes.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM01]  mitre_attack=[T1098, T1078]  cwe=[CWE-250, CWE-272, CWE-269]
- **nist_families:** AC, IA, SC, CM

### Long-lived provider API keys with no rotation cadence or automation

- **Threat:** Multi-provider LLM/tool API keys are issued once and never rotated, with no documented cadence and no automated rotation path. Agent systems leak keys through many channels (execution logs, generated code, artifacts, sub-agent context, tool outputs); without rotation a single leak is permanent and grants standing model/tool access. The lens here is rotation cadence plus automation and expiry, not the at-rest storage (that is Confidentiality).
- **Grounding:** OWASP LLM02 Sensitive Information Disclosure; LLM10 Unbounded Consumption  |  ATLAS LLM Meta-Prompt Extraction (AML.T0056); ML Model Extraction/Stealing (AML.T0044)  |  MAESTRO L1 Foundation Models; L2 Data Operations; L4 Deployment & Infrastructure
- **SIA:** SIA uses multiple model-provider API keys across the Meta/Target/Feedback loop. Keys are static for the life of the project; agent_execution.json and generated target code can echo or exfiltrate them. With no rotation cadence, a key surfaced in any gen_n artifact stays valid indefinitely and bills/uses every provider, also feeding the LLM10 unbounded-consumption blast radius.
- **taxonomy_mappings:** owasp_llm_top10=[LLM02, LLM10]  mitre_attack=[T1552.001, T1078.004]  cwe=[CWE-798, CWE-322]
- **nist_families:** IA, SC, AC, SI

### No ephemeral sandbox per code-execution (reused or persistent exec environment)

- **Threat:** Agents that generate-and-execute code (or call code-exec tools) run inside a long-lived, reused, or mutable compute environment instead of a fresh ephemeral sandbox torn down after each invocation. State, installed packages, dropped files, and harvested credentials persist across executions, so one poisoned/injected execution implants persistence that survives into later tasks and other agents. Lens: ephemeral compute boundary per exec plus immutable-infra teardown, not the output-sanitization of what the code returns (that is Integrity/Output Handling).
- **Grounding:** OWASP LLM06 Excessive Agency; LLM05 Improper Output Handling  |  ATLAS LLM Prompt Injection (AML.T0051); Backdoor ML Model (AML.T0018)  |  MAESTRO L4 Deployment & Infrastructure; L3 Agent Frameworks
- **SIA:** SIA's generated target_agent.py executes arbitrary Python each generation. If generations share a working environment (installed deps, files under runs/, env vars) rather than a per-gen disposable sandbox, a malicious or reward-hacking generation can plant artifacts/credentials that persist into gen_n+1 and across runs. Ephemeral fix: one disposable sandbox per gen_n exec, destroyed at generation end, with no writable carry-over outside the logged artifact.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM05]  mitre_attack=[T1059, T1610]  cwe=[CWE-1188, CWE-668]
- **nist_families:** SC, CM, SI, AC

### Sub-agent / spawned-agent credentials lack independent expiry & revocation

- **Threat:** When an agent spawns sub-agents (or peers in a multi-agent system), they inherit or are handed the parent's credential with no shorter TTL and no independent revocation handle. A compromised, impersonating, or colluding sub-agent therefore holds a credential that cannot be revoked without killing the whole system, and that outlives the sub-task. Lens: per-sub-agent ephemeral credential issuance with bounded session lifetime and targeted revocation, not proving which agent is genuine (Authenticity) or auditing what it did (Non-Repudiation).
- **Grounding:** OWASP LLM06 Excessive Agency; LLM01 Prompt Injection  |  ATLAS LLM Prompt Injection (AML.T0051); LLM Jailbreak (AML.T0054)  |  MAESTRO L7 Agent Ecosystem; L3 Agent Frameworks; L6 Security & Compliance
- **SIA:** SIA's Meta-Agent, Target Agent, and Feedback Agent form a multi-stage agent set sharing the same provider keys with no per-stage TTL or per-stage revocation. A hijacked Feedback Agent (which rewrites the target across generations) holds a credential indistinguishable in lifetime from the Meta-Agent's; you cannot revoke just the Feedback stage. Ephemeral fix: each stage gets its own short-lived, independently-revocable token scoped to its step.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM01]  mitre_attack=[T1098, T1136]  cwe=[CWE-269, CWE-668]
- **nist_families:** AC, IA, SC

### Compromised-generation credential revocation & blast-radius containment

- **Threat:** In a self-improving / autonomous-loop system there is no fast path to revoke the credentials and tokens a single bad generation (or rogue loop iteration) touched, and no kill-switch to expire its compute. When a generation reward-hacks, gets poisoned, or is injected, its still-valid credentials let the damage propagate into subsequent generations and outward to providers/tools. Lens: scoped revocation of one generation's secrets plus ephemeral-compute kill on detection, the containment-by-expiry side, distinct from detecting the misbehavior (Resilient) or auditing it (Non-Repudiation).
- **Grounding:** OWASP LLM04 Data & Model Poisoning; LLM06 Excessive Agency; LLM10 Unbounded Consumption  |  ATLAS Backdoor ML Model (AML.T0018); Data Poisoning (AML.T0020)  |  MAESTRO L5 Evaluation & Observability; L2 Data Operations; L4 Deployment & Infrastructure
- **SIA:** SIA evolves target_agent.py over --max_gen generations optimizing a scalar metric against a benchmark with held-out private ground truth (data/private/, evaluate.py). A generation that reward-hacks or is poisoned keeps valid provider keys and can keep touching data/private and artifacts under runs/run_id/gen_n. Without per-gen credential expiry/revocation and a loop kill-switch, the compromise cannot be contained to one gen_n. Ephemeral fix: bind each generation's secrets to that gen, auto-expire on completion, and revoke-on-detection before the next gen starts.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM06, LLM10]  mitre_attack=[T1485, T1078]  cwe=[CWE-672, CWE-269]
- **nist_families:** AC, CP, SC, RA, SI

### Unbounded agent session / memory TTL (no autonomous-loop time or turn budget)

- **Threat:** Agent sessions, conversational/long-term memory, and autonomous task loops have no maximum lifetime, no turn/iteration budget, and no idle expiry. Stale memory and never-expiring sessions keep injected instructions, harvested secrets, and accumulated agency alive indefinitely, and an unbounded loop is itself an excessive-agency plus unbounded-consumption hazard. Lens: session/memory TTL and loop budget as an expiry control, not the content-trust of memory entries (Integrity) nor consumption rate-limiting framed purely as availability.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency; LLM08 Vector & Embedding Weaknesses  |  ATLAS LLM Prompt Injection (AML.T0051)  |  MAESTRO L3 Agent Frameworks; L2 Data Operations; L4 Deployment & Infrastructure
- **SIA:** SIA's loop is bounded by --max_gen, which gives it a generation budget, a partial ephemeral control. But within/after a run, agent_execution.json logs and per-gen memory/artifacts under runs/run_id/gen_n have no TTL: secrets and injected context captured in one generation's log persist with no expiry and can be re-ingested by later generations. Ephemeral fix: TTL on session/memory artifacts and an explicit idle/turn budget inside each generation, not just the cross-generation cap.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10, LLM06]  mitre_attack=[T1496]  cwe=[CWE-770, CWE-613]
- **nist_families:** AC, SC, SI, AU

**Multi-agent / self-improvement coverage:** MULTI-AGENT: Pattern 4 (sub-agent credentials lack independent expiry/revocation) is the dedicated multi-agent surface for this lens, covering spawned sub-agents and peer agents inheriting parent credentials with no shorter TTL and no per-agent revocation handle, the lifecycle root-cause that lets agent-impersonation and inter-agent collusion threats persist (MAESTRO L7). Pattern 1 (standing broad agency) and Pattern 5 (compromised-generation revocation) also bite in the multi-agent case: shared standing keys across a Meta/Target/Feedback agent set mean one hijacked agent wields every agent's agency, and lack of scoped revocation means a colluding/Sybil agent's credential cannot be expired in isolation. SELF-IMPROVEMENT (SIA-class): fully covered by Patterns 3 and 5 as the core. Pattern 3 (ephemeral sandbox per code-exec) addresses the self-modifying generate-and-execute loop where each generation runs arbitrary code and must not carry persistence forward. Pattern 5 (compromised-generation credential revocation plus loop kill-switch) is the self-improvement containment pattern, binding each generation's secrets to that gen, auto-expiring on completion, and revoking-on-detection so a reward-hacked or poisoned generation cannot propagate still-valid credentials into gen_n+1 or out to providers/data/private. Pattern 2 (key rotation cadence) and Pattern 6 (session/memory TTL) close the loop: across N generations, static keys and never-expiring per-gen memory artifacts are exactly where a self-improving system accumulates standing, leakable, long-lived credential exposure.

**Lens boundaries:** Deliberately routed to adjacent APD goals (named, not designed here): (1) Secret/key AT-REST storage, encryption, and KMS/vault key-management hygiene for provider keys goes to CONFIDENTIALITY; this lens owns only the rotation cadence, TTL, and expiry of those secrets, not how they are protected at rest. (2) Encryption of inter-agent communication and tool-call channels in transit goes to CONFIDENTIALITY. (3) Identity strength, proving a sub-agent or peer agent is genuine (agent authentication, anti-impersonation, anti-Sybil binding), goes to AUTHENTICITY; I own per-sub-agent credential expiry/revocation, Authenticity owns whether the credential proves who the agent is. (4) Audit/logging of which credential was used, by which agent, and access-event recording (including agent_execution.json as an audit trail) goes to NON-REPUDIATION. (5) Detection of reward-hacking, poisoning, jailbreak, anomalous tool use, and reuse-detection alerting goes to RESILIENT; I own containment-by-expiry and revocation once detection fires, Resilient owns the detection signal. (6) Content-trust and poisoning-resistance of memory entries, feedback/training data, and tool outputs goes to INTEGRITY / data-and-model-poisoning; I own memory TTL, not whether a retained entry is trustworthy. (7) Tamper-evidence and append-only guarantees on run artifacts under runs/run_id/gen_n go to IMMUTABILITY; I own ephemeral teardown of compute and expiry of artifacts, not their immutable-record posture.

## Authenticity  (common-patterns/authenticity.md)

### Self-produced agent code emitted unsigned / no per-generation provenance

- **Threat:** A self-improving loop writes executable agent code each generation but the generated artifact carries no signature or provenance attestation binding it to the producing agent, model+prompt, and parent generation. A poisoned or smuggled generation (via prompt injection into the rewrite step) executes with full privilege and there is no authentic chain establishing which agent/model authored which executable across the run. This is the SIA-class root-of-trust gap: the system trusts code it produced about itself without proving the code is what the loop intended to produce.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM05 Improper Output Handling; LLM01 Prompt Injection; LLM03 Supply Chain  |  ATLAS LLM Prompt Injection (AML.T0051); Backdoor ML Model (AML.T0018); LLM Jailbreak (AML.T0054)  |  MAESTRO L3 Agent Frameworks; L1 Foundation Models; L4 Deployment & Infrastructure
- **SIA:** SIA's Meta-Agent and Feedback Agent generate/rewrite target_agent.py each generation under runs/run_id/gen_n/; that file EXECUTES arbitrary Python. SIA does not sign each generated target_agent.py nor attest the (model, prompt-hash, parent-gen) provenance, so there is no authentic binding between a given executable and the generation that was supposed to produce it. A prompt-injected rewrite is indistinguishable from a legitimate one. Pattern: require an in-toto/Sigstore-style attestation per generation — sign the artifact hash with a per-run signing identity and record producing-agent + model + parent-gen-hash — verified before the Target Agent executes it.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM05, LLM03]  mitre_attack=[T1059]  cwe=[CWE-345, CWE-494, CWE-913]
- **nist_families:** SI, SR, CM, AC

### Agent / sub-agent workload identity absent — shared API keys, no SPIFFE-class identity

- **Threat:** Each agent and sub-agent in a multi-agent system acts under a shared static credential (a pooled API key or service token) rather than a cryptographic per-workload identity. There is no way to authenticate WHICH agent is making a call, so a compromised or rogue sub-agent is indistinguishable from a legitimate one, lateral movement is unbounded, and the root of trust collapses to one shared secret. This is the foundational workload-identity gap that every per-agent authenticity claim depends on.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM02 Sensitive Information Disclosure  |  ATLAS Valid Accounts (credential reuse across agents)  |  MAESTRO L3 Agent Frameworks; L4 Deployment & Infrastructure; L7 Agent Ecosystem
- **SIA:** SIA drives multiple model-provider API keys shared across the Meta-Agent, Target Agent, and Feedback Agent with no per-role workload identity; any component (or injected code) presents the same key set, so provider-side and internal calls cannot be attributed to a specific agent role. Pattern: issue SPIFFE/SPIRE (or equivalent) per-agent-role workload identities and broker provider keys behind that identity (IA-9 service authentication) so each agent authenticates as itself, not as the pool.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06]  mitre_attack=[T1078, T1552]  cwe=[CWE-522, CWE-306]
- **nist_families:** IA, SC, AC

### Inter-agent messages unsigned — agent impersonation, Sybil identities, goal-manipulation cascade

- **Threat:** Messages, task delegations, and goal/state updates passed between agents are not cryptographically signed or sender-authenticated. An adversary (or a compromised peer) can impersonate a trusted agent, spin up Sybil identities to dominate consensus/voting, or inject forged goal updates that cascade through the agent graph — none of which the receiving agents can detect because there is no authentic sender binding on the payload. This is the multi-agent authenticity core: trust between agents must be cryptographic, not positional.
- **Grounding:** OWASP LLM01 Prompt Injection; LLM06 Excessive Agency; LLM09 Misinformation  |  ATLAS LLM Prompt Injection (indirect, agent-to-agent); Erode ML Model Integrity  |  MAESTRO L7 Agent Ecosystem; L3 Agent Frameworks; L2 Data Operations
- **SIA:** SIA's Feedback Agent feeds rewrite instructions / evaluation signals to the generation step and the Target Agent logs to agent_execution.json; these inter-agent handoffs are unsigned, so a tampered or forged feedback/goal message (e.g. injected via the executed task's output) cannot be distinguished from authentic Feedback-Agent output and steers the next generation. Pattern: sign every inter-agent payload with the sender's per-agent workload identity (detached signature over message + nonce + parent-message-hash); receivers verify sender authenticity and reject unsigned/Sybil senders before acting.
- **taxonomy_mappings:** owasp_llm_top10=[LLM01, LLM06]  mitre_attack=[T1565.002]  cwe=[CWE-345, CWE-290, CWE-347]
- **nist_families:** IA, SC, SI

### Tool / plugin / MCP-server authenticity not verified before binding

- **Threat:** An agent discovers and binds tools, plugins, or MCP servers (and their schemas) at runtime without verifying the publisher's signature or provenance. A malicious or tampered tool is loaded with the agent's privileges, can exfiltrate via tool calls, and can return forged 'tool descriptions' that hijack the agent (tool-description / line-jumping injection). The agent's effective trust boundary extends to every tool it loads, so tool authenticity is a root-of-trust concern.
- **Grounding:** OWASP LLM03 Supply Chain; LLM06 Excessive Agency; LLM01 Prompt Injection  |  ATLAS ML Supply Chain Compromise (AML.T0010); LLM Prompt Injection (via tool/plugin metadata)  |  MAESTRO L7 Agent Ecosystem; L3 Agent Frameworks; L4 Deployment & Infrastructure
- **SIA:** SIA is built on the Claude Agent SDK + OpenHands and the generated target_agent.py can invoke arbitrary tools/Python; tools and OpenHands components are loaded without signature/provenance verification, so a tampered dependency or injected tool runs inside the execution sandbox with the agent's privileges. Pattern: require signed tool/plugin manifests and verified MCP-server identity (publisher signature + allowlisted root) checked at bind-time, not trust-on-first-use.
- **taxonomy_mappings:** owasp_llm_top10=[LLM03, LLM06]  mitre_attack=[T1195.002, T1505]  cwe=[CWE-345, CWE-494, CWE-829]
- **nist_families:** SR, SI, CM

### Model & dependency provenance unattested — no SBOM / SLSA for models, frameworks, and agent stack

- **Threat:** The system cannot prove the authenticity and provenance of the models it calls, the agent frameworks it runs on, and the package dependencies in the agent runtime. Without an SBOM and build/source attestation (SLSA, in-toto), a swapped model endpoint, a backdoored fine-tune, or a poisoned framework dependency is undetectable — the supply chain for an autonomous agent is its weights, its framework, and its tools, and none of it is attested.
- **Grounding:** OWASP LLM03 Supply Chain; LLM04 Data & Model Poisoning  |  ATLAS ML Supply Chain Compromise (AML.T0010); Backdoor ML Model (AML.T0018); Publish Poisoned Datasets / Poison Training Data  |  MAESTRO L1 Foundation Models; L2 Data Operations; L4 Deployment & Infrastructure
- **SIA:** SIA pulls multiple foundation models via provider APIs and runs on the Claude Agent SDK + OpenHands with a Python dependency tree, but produces no SBOM or provenance attestation for the model versions or the framework/dep stack feeding each generation under runs/run_id/. A silently changed model behind an endpoint, or a poisoned dependency, would alter every downstream generation undetected. Pattern: emit an SBOM (and SLSA-style build provenance) covering models-by-version, framework, and deps; pin and verify provenance at run start and on dependency change.
- **taxonomy_mappings:** owasp_llm_top10=[LLM03, LLM04]  mitre_attack=[T1195.001, T1195.002]  cwe=[CWE-1357, CWE-345, CWE-494]
- **nist_families:** SR, SI, CM, RA

### Human operator of the autonomous loop authenticated below the required AAL

- **Threat:** The humans who launch, configure, or approve runs of an autonomous/self-modifying loop — setting --max_gen, approving generations, holding the provider keys, releasing a self-improved artifact — are authenticated with weak or phishable factors (password-only or SMS-OTP) rather than phishing-resistant MFA at the assurance level the blast radius demands. Compromising one operator hands an attacker the steering wheel of a system that writes and executes its own code, so operator AAL is an authenticity control on the loop's root of trust.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM02 Sensitive Information Disclosure  |  ATLAS Valid Accounts (operator credential compromise)  |  MAESTRO L6 Security & Compliance; L4 Deployment & Infrastructure; L3 Agent Frameworks
- **SIA:** An operator launches SIA runs (--max_gen, benchmark/private ground-truth config, provider keys) and would approve promotion of a self-improved target. If that operator surface is password+SMS rather than FIDO2/WebAuthn, a single phish lets an attacker run the loop, redirect keys, or promote a poisoned generation. Pattern: require phishing-resistant MFA (NIST 800-63B AAL2/AAL3 by blast radius) and step-up authentication for run-launch, max-gen change, key access, and artifact-promotion actions.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06]  mitre_attack=[T1078, T1621, T1556.006]  cwe=[CWE-308, CWE-1390]
- **nist_families:** IA, AC

**Multi-agent / self-improvement coverage:** MULTI-AGENT surface is covered by three patterns that together establish cryptographic (not positional) trust between agents: (1) per-agent/sub-agent workload identity (SPIFFE/SPIRE) so every agent authenticates as itself rather than as a shared key pool — the prerequisite for any per-agent authenticity claim; (2) signed inter-agent payloads, which is the direct counter to the MAESTRO multi-agent threats called out in scope — agent impersonation, Sybil identities (sender binding defeats fabricated identities), inter-agent communication interception, and goal-manipulation cascades (each goal/task message is sender-authenticated, so a forged goal update cannot propagate through the agent graph); and (3) tool/plugin/MCP-server authenticity for the L7 Agent Ecosystem trust boundary an agent extends every time it binds a peer capability. SELF-IMPROVEMENT is covered as a first-class sub-surface by per-generation signing/provenance of self-produced agent code — the SIA-class core: each generated executable is signed and attested (producing-agent, model+prompt-hash, parent-gen-hash) and verified before execution, so a prompt-injected or smuggled rewrite cannot masquerade as a legitimate generation. Self-improvement is further protected by model & dependency provenance (SLSA/SBOM over models-by-version + framework + deps, since a self-improving loop's supply chain is its own outputs feeding the next iteration) and by operator-AAL on the loop-control surface (run-launch, --max_gen, key access, artifact promotion). Every pattern is instantiated concretely against SIA's Meta-Agent / Target Agent / Feedback Agent, target_agent.py generation, runs/run_id/gen_n artifacts, multi-provider keys, and the OpenHands/Claude-Agent-SDK stack.

**Lens boundaries:** Routed OUT of Authenticity by design: (1) Audit attribution / actor-to-action accountability and tamper-evident logging of agent_execution.json — the binding of a verified identity to a recorded action belongs to NON-REPUDIATION; this lens establishes the authentic identity, that goal records who-did-what with it. (2) Credential/token/signing-key LIFETIME and rotation — per-generation signing-key TTL, workload-credential rotation, ephemeral per-run CAs, and provider-key short-livedness belong to EPHEMERAL; this lens asserts that an identity/signature exists and chains to a root of trust, not how long it lives. (3) Data CONFIDENTIALITY — protecting the held-out private ground truth (data/private/, evaluate.py), provider keys at rest, and inter-agent channel encryption belongs to CONFIDENTIALITY; this lens signs payloads for sender-authenticity, it does not encrypt them. (4) INTEGRITY-of-content concerns — validating/sanitizing executed tool output and untrusted task input (the injection payload itself), and the correctness of signature-VALIDATION logic, cross-cut Integrity; this lens owns the existence and provenance of the signature/identity, Integrity owns input validation and the validation routine's soundness. (5) IMMUTABILITY — the append-only, tamper-evident HISTORY of generations and artifact provenance records belongs to Immutability; this lens produces the per-generation attestation, that goal makes the chain of them unforgeable over time. (6) Sandbox/privilege CONFINEMENT of arbitrary Python execution (least-privilege blast-radius reduction) is an Excessive-Agency/Confinement concern routed to the agency/authorization goal; this lens only authenticates the code, it does not bound what authenticated code may do.

## non-repudiation  (common-patterns/non-repudiation.md)

### Consequential-action audit completeness vs the defined agentic action surface

- **Threat:** Autonomous agents take many consequential actions per task — tool/function calls, self-modification (writing/replacing agent code), secret/API-key use, sub-agent delegation, and eval-data access — but logging covers only the obvious LLM request/response pair. Any unaudited action class (a shelled-out command, a file write, a key use) leaves a consequential act with no record, so it cannot be attributed or reconstructed after the fact. This is the dominant real-world non-repudiation gap on agentic systems.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM05 Improper Output Handling; LLM10 Unbounded Consumption  |  ATLAS LLM Prompt Injection (AML.T0051) as the act that must be reconstructable; ML-Enabled Product or Service abuse leaving no audit trail  |  MAESTRO L3 Agent Frameworks (tool-call/orchestration surface); L5 Evaluation & Observability (the audit/trace plane itself); L6 Security & Compliance (cross-cutting accountability)
- **SIA:** SIA's Target Agent executes arbitrary Python and logs to agent_execution.json; the consequential surface to audit is broader than that file — every tool call, each model-provider API-key use, every write that produces target_agent.py, and every read under data/private/ via evaluate.py. The check is: enumerate that surface and confirm agent_execution.json (and run artifacts under runs/run_id/gen_n/) actually capture each class, not just the task-level prompt/response.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM05]  mitre_attack=[T1059]  cwe=[CWE-778, CWE-223]
- **nist_families:** AU, SI, CM

### Per-entry actor attribution across agent / sub-agent / human / generation

- **Threat:** In multi-agent and self-improving loops, many distinct principals act: a Meta-Agent, a Target Agent, a Feedback Agent, delegated sub-agents, the human operator, and a specific generation iteration. If audit entries attribute actions to a shared 'system' actor or a single shared service account, you cannot answer 'which agent/sub-agent/generation/human did this' — defeating dispute resolution, insider-action attribution, and goal-manipulation-cascade tracing across the agent graph. Attribution must include the acting principal AND the delegation chain (who delegated to whom) and the generation/run context.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM09 Misinformation (mis-attributed agent outputs)  |  ATLAS LLM Jailbreak / Prompt Injection where the injected instruction is executed by a sub-agent and must be traced back to the responsible principal  |  MAESTRO L3 Agent Frameworks; L7 Agent Ecosystem (inter-agent delegation, impersonation, Sybil identities); L6 Security & Compliance
- **SIA:** Each artifact under runs/run_id/gen_n/ should carry attribution: which agent role (meta/target/feedback), which generation n (from --max_gen), and which model provider produced each step. SIA's per-generation rewrites mean 'who modified the target' is generation-scoped — the audit entry must name the Feedback Agent and the generation, not just 'sia'. Sub-agent delegation in the OpenHands/Claude-Agent-SDK substrate must record the delegating principal.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06]  mitre_attack=[T1078]  cwe=[CWE-778, CWE-117]
- **nist_families:** AU, AC, IA

### Signed, hash-chained decision/action traces (gap-evident, attributable record)

- **Threat:** Audit value for non-repudiation depends on a tamper-evident, gap-evident record: without per-stream hash-chaining and entry signing, a missing or reordered action cannot be detected, and an actor can plausibly deny an entry or claim an entry was forged. For agentic loops this matters most on the decision trace — the chain of tool calls and self-modifications that led to a consequential outcome — so the sequence itself is provably complete and bound to its producer. (Tamper-resistance of stored records is Immutability's lens; here the concern is the chain/signature existing so attribution and completeness are provable.)
- **Grounding:** OWASP LLM05 Improper Output Handling; LLM06 Excessive Agency  |  ATLAS Erode ML Model Integrity / log tampering to repudiate actions; chain heads anchored externally to resist this  |  MAESTRO L5 Evaluation & Observability; L6 Security & Compliance
- **SIA:** The cross-generation decision trace (gen_0 -> gen_n target rewrites and the tool calls within each) should be hash-chained per run and entries signed, with chain heads anchored outside the runs/ tree (separate trust domain). This makes 'generation k's rewrite is missing/forged' detectable and binds each rewrite to the Feedback Agent that produced it.
- **taxonomy_mappings:** owasp_llm_top10=[LLM05, LLM06]  mitre_attack=[T1565.001]  cwe=[CWE-778, CWE-345]
- **nist_families:** AU, SC, SI

### Reliable, ordered time source across the loop and across generations

- **Threat:** Ordering of actions across long-running autonomous loops, across multiple concurrent agents/sub-agents, and across generations depends on a disciplined time source. If timestamps are unsynchronized local clocks with no NTP discipline, drift bounds, or monotonic ordering guarantee, you cannot establish the true sequence of consequential actions — which tool call preceded which self-modification, whether a sub-agent acted before or after a delegation — undermining causal reconstruction and dispute resolution. Concurrency across multi-agent systems requires a logical/monotonic ordering anchor in addition to wall-clock time.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM09 Misinformation (false ordering narrative)  |  ATLAS n/a (ATLAS has no specific time-source technique; ordering reliability supports reconstruction of any logged attack technique)  |  MAESTRO L4 Deployment & Infrastructure (clock/NTP topology); L5 Evaluation & Observability; L7 Agent Ecosystem (cross-agent ordering)
- **SIA:** SIA writes per-generation artifacts under runs/run_id/gen_n/; ordering across generations and across the tool calls inside a generation needs a reliable time source plus a monotonic per-run sequence number. The check surfaces as an uncertainty/blocked finding when no time-source specification (NTP topology, drift bounds, behavior on time-source failure, monotonic ordering across concurrent agents) is in evidence.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06]  mitre_attack=[]  cwe=[CWE-829, CWE-223]
- **nist_families:** AU, SC

### Audit-read/alter access control with segregation of duties from the agents

- **Threat:** If the same principals that run the loop (or the agents themselves, including a self-modifying Feedback Agent) can read or write their own audit logs, attribution can be silently curated and audit-of-audit-access is lost — an insider or a compromised agent can identify what was observed and adjust behavior, or a self-improving agent can learn to suppress records of its own consequential actions. Audit access must be gated by a role separate from operational/agent roles, and audit-read events must themselves be audited (SoD). (Whether records can be altered once written is Immutability; here the concern is who is authorized to touch the audit stream and that those touches are themselves recorded.)
- **Grounding:** OWASP LLM06 Excessive Agency; LLM02 Sensitive Information Disclosure (audit content sensitivity inheritance)  |  ATLAS LLM Meta-Prompt Extraction / observability-plane tampering where an agent reads or curates its own traces to repudiate actions  |  MAESTRO L5 Evaluation & Observability; L6 Security & Compliance; L3 Agent Frameworks (agent's own write scope)
- **SIA:** SIA agents have filesystem and code-execution reach; if the Target/Feedback Agent's execution context can write or prune runs/run_id/gen_n/ logs or agent_execution.json, there is no SoD between actor and auditor. The pattern checks that audit sinks live outside agent-writable scope and that any read of the trace plane is recorded independently — critical because a self-improving agent could otherwise optimize toward concealing its own records.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM02]  mitre_attack=[T1070, T1562.008]  cwe=[CWE-732, CWE-778]
- **nist_families:** AU, AC, SI

### Audit shipping reliability to a durable off-host sink

- **Threat:** Long autonomous runs generate audit on the same host/process that executes consequential actions; fire-and-forget shipping with a single broker/sink and no buffer produces silent audit loss exactly during the high-activity windows (a runaway loop, an unbounded-consumption episode, a cascade) that most need reconstruction. Audit must reach a durable off-host sink with buffering, delivery acknowledgement, and back-pressure handling so the record survives the agent host's failure or termination.
- **Grounding:** OWASP LLM10 Unbounded Consumption; LLM06 Excessive Agency  |  ATLAS n/a (no specific ATLAS technique; reliable shipping preserves the evidence base for any logged technique)  |  MAESTRO L4 Deployment & Infrastructure (audit pipeline/broker topology); L5 Evaluation & Observability
- **SIA:** SIA persists artifacts under a local runs/ tree; if a generation crashes, is killed for exceeding budget, or the host is reclaimed, locally-buffered audit can be lost. The check is whether agent_execution.json and per-generation traces are shipped to a durable sink outside the run host with acknowledgement, rather than relying on the local filesystem surviving the run.
- **taxonomy_mappings:** owasp_llm_top10=[LLM10]  mitre_attack=[]  cwe=[CWE-778, CWE-779]
- **nist_families:** AU, CP, SI

**Multi-agent / self-improvement coverage:** Multi-agent surface: the actor-attribution pattern (Pattern 2) is built around the multi-principal reality — meta/target/feedback agents, delegated sub-agents, and the human operator must each be attributable per entry, including the delegation chain (who delegated to whom), which directly addresses MAESTRO L7 inter-agent threats (impersonation, Sybil identities, goal-manipulation cascades) by ensuring every link in a cascade is recorded against its responsible principal. The time-source pattern (Pattern 4) adds the cross-agent ordering anchor (monotonic sequence + synchronized clock) needed to reconstruct the true order of actions across concurrent agents, so a cascade can be traced causally rather than guessed. The SoD pattern (Pattern 5) ensures no single agent in the mesh can read/curate the shared audit plane. Self-improvement surface: self-modification is treated as a first-class consequential action class in Pattern 1 (every write that produces target_agent.py must be logged) and as a generation-scoped attribution requirement in Pattern 2 (which generation, which Feedback Agent rewrote the target). Pattern 3 hash-chains the cross-generation decision trace so the gen_0 -> gen_n rewrite sequence is provably complete and each rewrite is bound to its producer. Pattern 5 explicitly calls out the self-improving-agent risk that a Feedback Agent could optimize toward suppressing records of its own actions, requiring audit sinks outside agent-writable scope. Together these make the full SIA loop (Meta -> Target -> Feedback across --max_gen generations, with eval-data access and multi-provider key use) auditable, attributable, ordered, tamper-evident, access-controlled, and durably shipped.

**Lens boundaries:** Routed to Immutability: whether audit records can be altered or deleted once written — WORM storage, retention enforcement, write-once guarantees on runs/ artifacts. My patterns require the hash-chain/signature to EXIST (so gaps and forgeries are detectable and attribution is provable) and require audit sinks to sit outside agent-writable scope, but the durability/tamper-resistance of the stored record itself is Immutability's lens. Routed to Authenticity: the STRENGTH of the actor identity that populates the attribution field — agent/sub-agent identity issuance, mutual authentication between agents, key management for signing identities, and anti-impersonation/anti-Sybil identity proofing. My Pattern 2 consumes whatever principal identity exists and demands it be recorded per entry, but how trustworthy that identity is (was the Feedback Agent's identity strongly authenticated, can a Sybil agent forge a principal) belongs to Authenticity. Routed to Confidentiality: protection of sensitive content that the audit log inherits (secrets, private ground truth under data/private/, PII in traces) — I note audit-content sensitivity as a driver for access control (Pattern 5) and flag it via related_concerns, but encryption-at-rest/egress and classification of audit contents are Confidentiality's. Routed to Availability/Resilient: the audit-pipeline SLO and buffer-under-broker-outage behavior — I assert shipping must be reliable and durable (Pattern 6), but the pipeline's own uptime target and degraded-mode behavior are Availability's. Routed to Excessive-Agency/authorization goals: whether a consequential action was PERMITTED at all — my lens only asks that the action be recorded, not whether the agent should have been allowed to take it.

## Immutability  (common-patterns/immutability.md)

### Append-only generation lineage / provenance chain

- **Threat:** In a self-improving or multi-generation agent loop, the per-generation lineage (which parent agent produced which child, under which prompt/diff, scoring which metric) is written to a mutable store. A compromised or reward-hacking agent — or an operator covering a regression — can rewrite or delete a generation record so a later agent appears to have been derived from a benign ancestor, or so a poisoned/backdoored generation is hidden. The 'evolution' history becomes unverifiable and incident reconstruction across generations is impossible.
- **Grounding:** OWASP LLM04 Data & Model Poisoning; LLM03 Supply Chain; LLM06 Excessive Agency  |  ATLAS Backdoor ML Model (AML.T0018); Data Poisoning; LLM Meta-Prompt Extraction  |  MAESTRO L3 Agent Frameworks (self-improvement loop / generation graph); L2 Data Operations (lineage records as data); L5 Evaluation & Observability (lineage feeds eval reconstruction)
- **SIA:** SIA's Feedback Agent rewrites target_agent.py across generations under runs/run_id/gen_n/. The gen_n provenance chain (parent gen -> child gen, the rewrite diff, the model+key that produced it) must be append-only and hash-chained so gen_n's hash commits to gen_{n-1}'s head. Today these are plain files in runs/; a later generation can be back-edited or a generation silently dropped, breaking the lineage that explains how a high-scoring-but-malicious target was reached.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM03, LLM06]  mitre_attack=[T1565.001, T1070]  cwe=[CWE-345, CWE-471, CWE-353]
- **nist_families:** AU, SI, SR, CM

### WORM execution / decision traces (tool-call + action ledger)

- **Threat:** The agent's runtime trace — tool invocations, arguments, code it chose to execute, sub-agent dispatches, and the decision rationale per step — is logged to a mutable substrate with no append-only enforcement and no hash chaining. After an agent takes a harmful consequential action (deletes data, exfiltrates, executes attacker-supplied code via prompt injection), the trace can be altered or truncated to erase the offending tool call, defeating post-incident reconstruction. Mutable trace = functionally absent trace for autonomous-action accountability.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM05 Improper Output Handling; LLM01 Prompt Injection (originating trigger whose trace must survive)  |  ATLAS LLM Prompt Injection (AML.T0051); LLM Jailbreak  |  MAESTRO L5 Evaluation & Observability (the trace IS the observability substrate); L3 Agent Frameworks (tool-call mediation produces the trace); L7 Agent Ecosystem (cross-agent action traces)
- **SIA:** SIA's Target Agent logs the executed run to agent_execution.json. Because target_agent.py executes arbitrary Python, that log is the only record of what code ran and which tools/keys it touched. It must be append-only and hash-chained with the chain-head anchored outside the run directory so a self-modifying target cannot rewrite its own agent_execution.json to hide a destructive or exfiltrating tool call before the Feedback Agent scores it.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM05, LLM01]  mitre_attack=[T1070, T1070.004, T1565.001]  cwe=[CWE-778, CWE-117, CWE-345]
- **nist_families:** AU, SI, AC

### Immutable eval results / scores (anti-gaming of the optimization metric)

- **Threat:** The optimization-loop metric, benchmark scores, and held-out evaluation outputs are stored mutably and/or computed where the optimized agent can reach them. A self-improving system rewarded for a higher scalar metric has a direct incentive to edit its own recorded scores, overwrite a prior generation's results to fabricate monotonic improvement, or tamper with the held-out ground truth so the benchmark reports success regardless of behavior (reward hacking / Goodharting via record mutation rather than genuine improvement).
- **Grounding:** OWASP LLM04 Data & Model Poisoning (poisoning the eval/ground-truth); LLM09 Misinformation (fabricated success metrics); LLM06 Excessive Agency  |  ATLAS Data Poisoning (of the evaluation set); Evade ML Model (gaming the scorer)  |  MAESTRO L5 Evaluation & Observability (eval integrity is the core L5 concern); L2 Data Operations (held-out ground truth as protected data); L3 Agent Frameworks (reward channel back into the loop)
- **SIA:** SIA optimizes a scalar metric via evaluate.py against held-out private ground truth in data/private/. Eval results per gen_n and the private ground truth must be on a WORM/immutable substrate the Target Agent's executed code cannot write to. Scores should be hash-committed at compute time (anti-backdating) so a later generation cannot rewrite gen_{n-1} scores to invent improvement, and so the optimized agent cannot mutate data/private/ to make the benchmark always pass.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM09, LLM06]  mitre_attack=[T1565.001, T1070]  cwe=[CWE-345, CWE-639, CWE-707]
- **nist_families:** AU, SI, AC, RA

### Guardrail config-as-code: version history + drift detection (declared vs actual runtime)

- **Threat:** The agent's prompt/policy/tool-manifest and safety guardrails (allowed tools, scopes, sandboxes, rate/spend caps, sub-agent roster) are not held as signed, version-historied config-as-code, and there is no drift detection comparing the declared guardrail set against what is actually loaded at runtime. A prompt-injection payload, a self-modifying agent, or an operator can silently widen tool permissions or disable a guardrail at runtime while the declared policy file still looks safe; or rewrite the policy-repo history to erase that a dangerous capability was ever enabled. Declared-vs-actual divergence goes undetected.
- **Grounding:** OWASP LLM06 Excessive Agency; LLM01 Prompt Injection; LLM07 System Prompt Leakage (system-prompt/policy as drift target); LLM03 Supply Chain (tool-manifest provenance)  |  ATLAS LLM Prompt Injection; LLM Jailbreak; LLM Meta-Prompt Extraction  |  MAESTRO L3 Agent Frameworks (tool manifest + agent policy); L6 Security & Compliance (cross-cutting guardrail governance); L4 Deployment & Infrastructure (runtime-loaded config); L7 Agent Ecosystem (per-agent manifests in a multi-agent roster)
- **SIA:** SIA's Meta-Agent generates target_agent.py whose effective tool/permission surface (it can execute arbitrary Python and use multiple provider keys) IS the runtime guardrail state. The declared tool-manifest/policy and the Claude Agent SDK + OpenHands sandbox config must be version-historied with signed commits, and a drift check must compare declared-allowed capabilities against what each generated target actually loads/executes — otherwise a generation can grant itself broader capability than the declared policy and nothing flags the divergence.
- **taxonomy_mappings:** owasp_llm_top10=[LLM06, LLM01, LLM07, LLM03]  mitre_attack=[T1565.003, T1222, T1070]  cwe=[CWE-15, CWE-1059, CWE-345]
- **nist_families:** CM, SI, AC, SR

### Backup immutability for held-out ground truth & golden agent state (object/vault lock)

- **Threat:** The held-out evaluation ground truth, approved/known-good agent baselines, and run archives are backed up without object-lock / vault-lock immutability, so a single privileged credential (or a self-modifying agent that obtains filesystem/cloud reach) can delete or encrypt all copies. This destroys the only authoritative reference needed to detect that the optimization was gamed, roll back to a known-good generation, and prove what the benchmark and baselines were — a ransomware-class and anti-rollback exposure specific to autonomous loops that can act on infrastructure.
- **Grounding:** OWASP LLM04 Data & Model Poisoning; LLM10 Unbounded Consumption (uncontrolled loop can also exhaust/wipe storage); LLM06 Excessive Agency  |  ATLAS Data Poisoning (destroying clean reference data); Erode ML Model Integrity  |  MAESTRO L2 Data Operations (ground-truth datastore); L4 Deployment & Infrastructure (backup substrate); L1 Foundation Models (golden baseline checkpoints)
- **SIA:** SIA's data/private/ ground truth and the best-scoring agent checkpoints under runs/ must be backed up to an object-lock (compliance-mode) / vault-lock tier no run-time credential or generated target can downgrade or delete. Because target_agent.py executes arbitrary code with provider keys, an in-loop attacker could otherwise wipe both the live ground truth and its backups, making both gaming-detection and rollback to a safe generation impossible.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM10, LLM06]  mitre_attack=[T1485, T1490, T1486]  cwe=[CWE-345, CWE-693]
- **nist_families:** CP, MP, SI, RA

### Snapshot integrity of agent / shared memory state (multi-agent)

- **Threat:** Persistent agent memory and shared multi-agent state (vector store, scratchpad/blackboard, conversation/episodic memory, shared task queue) is snapshotted without integrity sealing or version history. One agent in a multi-agent system can silently mutate or back-date shared memory another agent relies on (memory poisoning, goal-manipulation cascades, impersonation via rewritten identity/context records), and the absence of immutable hash-sealed snapshots means there is no point-in-time state to diff against to prove tampering or to restore a clean memory baseline.
- **Grounding:** OWASP LLM04 Data & Model Poisoning (memory poisoning); LLM08 Vector & Embedding Weaknesses (shared vector memory); LLM01 Prompt Injection (injected content persisted into memory); LLM06 Excessive Agency  |  ATLAS Data Poisoning; LLM Prompt Injection (persisted/indirect); Backdoor ML Model (poisoned-memory backdoor)  |  MAESTRO L2 Data Operations (memory/vector store); L7 Agent Ecosystem (inter-agent shared state, impersonation, goal-cascade); L3 Agent Frameworks (memory subsystem)
- **SIA:** SIA is primarily a serial generation loop rather than a peer-to-peer multi-agent mesh, so shared-memory snapshot integrity partially applies: the cross-generation carry-over (prior agent_execution.json, accumulated runs/ artifacts a new generation reads as 'memory') should be snapshot-sealed and hash-versioned so a generation cannot rewrite the state a successor trusts. Full multi-agent shared-blackboard poisoning is n/a to SIA's current topology but is the dominant case for general multi-agent systems.
- **taxonomy_mappings:** owasp_llm_top10=[LLM04, LLM08, LLM01, LLM06]  mitre_attack=[T1565.001, T1070]  cwe=[CWE-345, CWE-471, CWE-913]
- **nist_families:** SI, AU, SC, CP

**Multi-agent / self-improvement coverage:** SELF-IMPROVEMENT (SIA-class) is covered end-to-end by four patterns that wrap the optimization loop in tamper-evidence: (1) append-only generation lineage hash-chains the gen_n provenance graph so a self-modifying agent cannot rewrite or drop the ancestry of a poisoned/backdoored generation; (2) WORM execution traces make agent_execution.json an append-only, externally-anchored ledger that an arbitrary-code-executing target cannot self-edit; (3) immutable eval results plus WORM-locked held-out ground truth is the load-bearing anti-reward-hacking control, preventing the optimized agent from fabricating metric improvement by mutating its own scores or poisoning data/private/; and (4) guardrail config-as-code drift detection compares each generation's actually-loaded capability surface against the signed declared policy, catching a generation that grants itself broader agency than declared. Backup immutability and cross-generation snapshot sealing close the rollback path so a clean generation and clean ground truth always survive. MULTI-AGENT is covered through the immutability lens by: WORM execution/decision traces extended to cross-agent dispatch and sub-agent action ledgers (so collusion or an impersonating agent's actions stay reconstructable); guardrail config-as-code carrying a PER-AGENT signed tool-manifest/roster with drift detection (catching a covertly-added Sybil agent or a widened sub-agent permission); and snapshot integrity of shared multi-agent memory/blackboard/vector state, the immutability-side defense against memory-poisoning and goal-manipulation cascades by providing an immutable hash-versioned point-in-time state to diff and restore. Together these supply the immutability evidence (tamper-evident records, declared-vs-actual drift, restorable clean state) needed to detect and unwind multi-agent collusion, impersonation, and cascade attacks, while the detection/attribution and channel-protection of those attacks route to adjacent goals.

**Lens boundaries:** Routed to Non-Repudiation (NOT designed here): whether trace/lineage/eval records EXIST at all and carry trustworthy per-agent attribution (which agent/key/operator authored an action or a rewrite), agent-identity signing of those records, and Sybil/impersonation attribution. Immutability assumes the record exists and protects it from post-hoc mutation; proving who made it and that it was made is Non-Repudiation. Routed to Confidentiality: encryption-at-rest of the WORM stores, held-out ground truth, run artifacts, and provider API keys, and read-access scoping of data/private/. Immutability protects against unauthorized MUTATION/DELETION, not unauthorized READING. Routed to Integrity: correctness/validation of config and data content in flight (schema/semantic validation of a tool manifest or a generation diff) as distinct from immutability's tamper-EVIDENCE-over-time of the stored history. Routed to Authenticity: the cryptographic identity and key custody behind signed commits and signed manifests; immutability relies on signed history existing but does not design the signing-key trust root. Routed to Availability: live recoverability/restore-time objectives of backups; immutability ensures backups CANNOT be deleted or altered, whereas whether restore actually works and meets RTO is Availability. Routed to Ephemeral: rotation cadence and time-bounded retention/expiry of keys and short-lived credentials; immutability sets retention floors and legal hold, while expiry ceilings and rotation are Ephemeral. The unbounded-loop runaway itself (spend/compute exhaustion, LLM10) routes to Availability/resilience except where it manifests as storage destruction of immutable classes, which is retained here.
