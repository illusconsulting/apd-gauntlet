## 1. Surface inventory

Core exposes the bearer-authenticated **REST API** (`/api/...`, port 8123) and the **WebSocket API** (`/api/websocket`, `auth_required`→`auth`→`auth_ok` handshake). ## 2. Persistence surface

Core persists secrets and config to `.storage` and history to the Recorder DB. The single most load-bearing at-rest fact: **`.storage` is written as plaintext UTF-8 JSON** — `Store._write_prepared_data` (`homeassistant/helpers/storage.py` L602-L618) calls `prepare_save_json` → `write_utf8_file`, with `self._private` controlling only file permissions (0600); there is **no encryption-at-rest**. This covers `.storage/auth` + `auth_provider.homeassistant` (bcrypt hashes, `rounds=12`), the refresh-token store (opaque `token_hex(64)` + per-token HS256 `jwt_key`), and `config_entries` / OAuth2 integration secrets. The **Recorder history DB** (`session_scope`, `homeassistant/helpers/recorder.py`) holds presence/geolocation/lock/alarm state. On the Supervisor side, **backups default to unencrypted** — `Backup.set_password` (`supervisor/backups/backup.py`) initializes `self._password = None`; the password (AES) is optional, making the full snapshot (config + recorder DB + tokens/secrets) the weakest-protected copy.

On the mobile clients: **Android Room `AppDatabase` is unencrypted SQLite** — `DatabaseModule.provideAppDatabase` builds it with no `openHelperFactory`/SQLCipher, so the `location_history` table (raw lat/long) and the `ServerSessionInfo` token rows sit in plaintext at rest. **iOS tokens** persist via `KeychainAccess` (`ServerManagerKeychain`) with no explicit `kSecAttrAccessible` set in `Sources/` (grep `.accessibility(` = 0 hits) → default `WhenUnlocked` (not `…ThisDeviceOnly`). The **Android mTLS client-cert private key** is the one hardware-protected secret: `KeyStoreRepositoryImpl` uses `KeyStore.getInstance("AndroidKeyStore")` (non-exportable).

## 3. Identity & auth code paths

Authentication is enforced at three chokepoints. **REST**: `auth_middleware` (`homeassistant/components/http/auth.py` L226-L261) accepts a bearer token (`async_validate_auth_header`), a signed query, or the supervisor unix socket; it sets `KEY_AUTHENTICATED` but does **not** reject — per-view decorators (`@require_admin`, `check_entity`, `user.is_admin`) enforce authorization. **WebSocket**: `AuthPhase.async_handle` validates the access token and registers a token-revocation callback. **Token model**: access tokens are HS256 JWTs (`async_create_access_token`) signed with the per-refresh-token `jwt_key`; `async_validate_access_token` verifies with 10s leeway and rejects revoked tokens / inactive users.

**Authorization decisions** resolve a long-standing brief unknown. The permission engine *is* enforced at runtime on the REST read path: `APIEntityStateView.get` calls `user.permissions.check_entity(entity_id, POLICY_READ)` and raises `Unauthorized` (contradicting the "not enforced yet" doc). However, `filter_entity_ids_by_permission` and `check_entity` **short-circuit to allow-all for any admin**, and **state writes require `user.is_admin`** with no per-entity write policy — so function-level authz is effectively admin-or-deny on the consequential path. `_OwnerPermissions` returns unconditional `True` (owner = all-access). On the Supervisor side, `SecurityMiddleware.token_validation` maps `SUPERVISOR_TOKEN` → app → `role_access[hassio_role]` URL regex; `ROLE_ADMIN` matches `.*`. The **mobile_app webhook bypasses this entire model**: `webhook_call_service` calls `hass.services.async_call` with a synthesized `registration_context` and no permission check — possession of the `webhook_id` is the only authenticator.

> *Limitation:* `trace_path` was not used for the cross-language hop set; identity paths were resolved by targeted `search_graph` + verbatim source reads. Go (os-agent) and Swift/Kotlin (mobile) auth paths were grounded by direct reads rather than call-graph tracing.

## 4. Audit emission sites

Consistent with the context brief's Non-Repudiation gap, **no dedicated security audit log was found in code**. Attribution exists only incidentally: the WS handshake calls `process_success_login` / `process_wrong_login`, and the REST middleware logs auth at DEBUG only. Non-Repudiation specialists should treat the absence as the finding (anchors: `cev-a1000009`, `cev-a1000018`, `cev-08000001`), not infer a log exists.

## 7. Gaps and limitations

- **Cross-repo auto-linking yielded 0 edges.** The CBM `cross-repo-intelligence` pass (run from 4 caller projects across 9 targets) found no automatically-derivable CROSS_* edges because HA composes inter-service URLs at runtime and uses unix-socket / D-Bus IPC for the host-root chain. The 6 boundary edges in §5 were grounded by direct code reads instead and emitted as `kind: edge` entries. The architecture-pass summary reported one pre-existing `CROSS_HTTP_CALLS` count on core that was not traversable as a relationship in the graph store (no rows on direct Cypher) — not reproduced.
- **`cev-` id derivation.** Under the MCP-only tool grant there is no shell/hashing primitive available, so the 8-hex `id` suffixes are assigned deterministically-by-construction (unique, stable, schema-valid) rather than recomputed from `sha256(qualified_name|line_range)` at author time. Each entry records the verbatim derivation input so the canonical id is recomputable offline.
- **Commit SHAs.** CBM `index_status` does not surface a commit SHA; per-repo SHAs were read from each checkout's `.git/HEAD` (detached-HEAD snapshots) or resolved branch ref. Two repos used branch refs (`mobile-apps-fcm-push`→`main`, `addons`→`master`); the rest were detached HEADs.
- **Approximate line ranges.** A few mobile/add-on anchors (`cev-e5000003`, `cev-f6000004`, `cev-f6000005`, `cev-09000001`) are node-level (class/file/config) where a precise sub-range was not material; these carry `L1-L1` or method-level ranges and are flagged in `notes`.
- **Light-touch repos with zero attributed entries.** No code anchors were emitted from: `operating-system`, `plugin-cli`, `plugin-dns`, `plugin-audio`, `plugin-multicast`, `plugin-observer`, `docker`, `docker-base`, `wheels`, `home-assistant-js-websocket`, and the four docs/peer repos (`companion.home-assistant`, `architecture`, `developers.home-assistant`, `home-assistant.io`). All are indexed and reachable; they are either thin plugin/build shells or design-intent docs already covered by the context brief, and were intentionally not deep-read per the run driver's depth-prioritization. This is **expected coverage, not a partial-index failure** — every code-bearing priority repo (core, supervisor, os-agent, cli, iOS, android, frontend, mobile-apps-fcm-push, addons) produced attributed entries.
- **Tracing method.** Identity/audit/persistence paths were resolved with targeted `search_graph` + verbatim `Read` of the indexed source rather than `trace_path` (kept queries sequential and small per the CBM concurrency caution against fanning out heavy queries on the 159k/208k-node core/supervisor graphs).
